## Non-Vacuity

**Every gate was observed red before it was trusted.** Three probes, listed in
`17.5-01-SUMMARY.md`. The one worth naming here is the third: removing a statement reds
the structural gate trivially, and only running against a server that never received the
statement shows the behavioural gate reads the catalog rather than the source. Without it,
T3 would be indistinguishable from a second copy of T1.

**The exposure was measured before the fix, not inferred.** A role holding the grants
Supabase hands `anon` read session text and identity hashes and deleted every row of
`runs`. A fix whose "before" state was never observed is a fix nobody can size.

## Manual-Only Verifications

| Behavior | Why Manual | Instructions |
|---|---|---|
| RLS lands on the production tables | The DDL applies on first use after a deploy | **DONE 2026-08-12, Fly release v13**, deployed by hand after three green merges produced no release. Both machines on v13; `/health` reports all three Postgres stores `reachable: true` with `sessions: 7`, `runs_recorded: 10`, `notes: 8` — **unchanged from the pre-deploy reading**. That is the verification that matters twice over: `ensure_schema` applies its DDL as one advisory-locked block, so a failed `ALTER … ENABLE ROW LEVEL SECURITY` would surface the store under `unreachable`, and an owner exemption that did *not* apply would show those counts as 0 with no error. Neither happened. `/`, `/demo`, `/metrics`, `/pricing`, `/ready` all 200. **CONFIRMED by the provider 2026-08-12: Advisors → Security reports the five `rls_disabled_in_public` errors and the `sensitive_columns_exposed` error on `runs` all cleared.** What replaced them is five `INFO` `rls_enabled_no_policy` notices, one per table — the expected and correct end state, since a policy is the only way to grant access back and none should exist. Recorded in `docs/OPERATIONS.md` and in the DDL comment so neither is "fixed" later. |
| The `REVOKE` of `anon`/`authenticated` grants | Those roles do not exist on a plain Postgres; the statement cannot live in code or CI | `docs/OPERATIONS.md` § "Row level security". **DONE 2026-08-12.** Confirmed by the end-state query across all five tables: `owner = postgres`, `rls_on = t`, `api_grants = (none)` on every row. The default-privilege check returned three rows granted by `supabase_admin` and **none by `postgres`** — that absence is the success signal, since a `postgres` row is what would grant `anon` on future app tables and a successful revoke deletes the row outright rather than emptying it. The `supabase_admin` entries are platform-managed, govern only objects that role creates, and are not alterable by `postgres`. **Corrected 2026-08-12 — the version first published here was wrong in a way that would have failed silently:** it used a bare `ALTER DEFAULT PRIVILEGES … REVOKE`, and default privileges are *per granting role*. Measured on a local stand-in reproducing Supabase's posture: run as `postgres`, the bare form left a table created afterwards by a different role holding **all seven privileges** for `anon`. The published script now requires `FOR ROLE <role from the pre-flight>`, and was re-verified end to end (14 grant rows → none; a table created after the script receives no grants; `anon` gets `permission denied` on read and write). |
| The Data API's actual state | Not observable from outside: the gateway rejects a missing `apikey` before the setting is consulted, so `/rest/v1` returns an identical 401 either way | Advisors → Security in the dashboard. User reports having toggled it off on 2026-08-12; **this phase does not verify it and does not depend on it.** |

Worth recording: **this phase's own framing was corrected mid-session.** The finding was
first reported as "confirmed live" on the strength of a `curl` returning PostgREST's 401.

API is enabled — it would have looked identical either way, before and after the toggle.

it is being used to distinguish is not weak evidence; it is no evidence.**
