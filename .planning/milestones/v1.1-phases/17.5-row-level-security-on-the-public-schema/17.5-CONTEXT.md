# Phase 17.5: Row level security on the public schema (hotfix) - Context

**Gathered:** 2026-08-12
**Status:** Executed same day
**Source:** A Supabase security-linter report the user brought to the session. No
discuss-phase run — the phase's one genuine open question (is the exposure reachable, and
what does the fix cost the running service) was answered by measurement before planning.

<domain>
## Phase Boundary

This phase makes every Postgres table the service creates deny every role except its
owner, so that a `public`-schema table exposed over a provider's HTTP API returns nothing
instead of everything.

It does **not** introduce policies, per-caller database authorisation, or any notion of
row ownership *at the database level*. Ownership already exists one layer up — Phase 12's
identity, enforced in application queries — and duplicating it as RLS policies would put
the same rule in two places that can disagree. RLS here is a deny-all boundary, nothing
more.

It also does not touch SQLite. The exposure is a property of a managed Postgres with an
HTTP API in front of it.

</domain>

<decisions>
## Implementation Decisions

### The fix lives in the schema constants, not a runbook

- **Every `POSTGRES_SCHEMA` ends with `ALTER TABLE … ENABLE ROW LEVEL SECURITY`**, applied
  under the advisory lock that already guards this DDL, re-issued on first use.
- **Rationale (load-bearing):** `migrate.py embeddings re-embed --to` creates a **new**
  corpus table on demand. A one-time SQL fix protects the tables that exist when it runs
  and silently misses every table created afterwards. The failure mode of the manual
  version is a table nobody remembers is unprotected — which is the same shape as the
  defect being fixed, where a control existed in code and was inert in production.
- Consequence accepted: the service issues a security-posture DDL statement on first use
  of every store. It is idempotent and cheap, and sits beside the `ADD COLUMN IF NOT
  EXISTS` migrations already there.

### `ENABLE`, never `FORCE`

- RLS exempts a table's **owner**, and the owner is the `DATABASE_URL` role because that
  role ran the DDL. The exemption is precisely what makes an empty policy set safe: the
  application is unaffected, everything else gets nothing.
- `FORCE` removes the exemption. With no policy defined, every application query would
  return **zero rows with no error** — sessions would appear empty rather than failing.
  That is the worst available failure mode, so it gets its own test rather than a comment.

### What the application deliberately cannot do

- **Revoking the provider's API-role grants stays an operator action.** `anon` and
  `authenticated` do not exist on a plain Postgres, so the statement would fail locally
  and in CI. Documented in `docs/OPERATIONS.md` with a read-only pre-flight.
- **Disabling the Data API is better than both** and is a dashboard setting. The user
  toggled it during this session. It is recorded as done-by-the-user and *not* verified by
  this phase — see the honesty note below.

### The one way this change could bite

- If the `DATABASE_URL` role does **not** own the tables, enabling RLS makes the service
  read zero rows silently. Verified safe by construction here (the app created every
  table, so it owns them), and the OPERATIONS pre-flight prints owner versus role so the
  assumption is checkable rather than assumed.

</decisions>

<measurement>
## What was measured before anything was written

Against a local PG17 + pgvector stand-in running this codebase's real DDL, with a
deliberately conservative owner role (`NOSUPERUSER NOBYPASSRLS`) and a second role granted
exactly what Supabase hands `anon` by default:

- **Before RLS:** the anon-grade role read session `task` and `state` (the visitor's
  question and the agent's answer), read `owner` identity hashes, and **deleted all four
  rows of `runs`** — no error.
- **After RLS:** zero rows visible, zero rows deleted, `INSERT` rejected. The owner still
  saw everything.
- **Cost to the service:** the full armed suite ran **801 passed / 1 skipped** both before
  and after — byte-identical, and matching the documented armed baseline.

`runs` is what makes this more than a privacy finding: `spend_since` sums that table and
is the daily spend cap's only input, so an emptied ledger reads as $0 spent and the one
control bounding the Anthropic bill stops bounding it.

</measurement>

<honesty>
## What this phase does not claim

**The Data API's state was not verified by this phase.** A `curl` of `/rest/v1/<table>`
returns the same PostgREST 401 whether or not the Data API is enabled, because the gateway
rejects a missing `apikey` before that setting is consulted — so the probe run before the
toggle and the probe run after it were always going to be identical, and neither is
evidence. Advisors → Security is the authoritative view. This was stated as a correction
during the session: the earlier "confirmed live" read more into that 401 than it supports.

**The finding itself does not rest on the probe.** Supabase's linter is the provider
reporting its own configuration, and `sensitive_columns_exposed` states outright that
`runs` is exposed via API without RLS. That is the evidence the phase acts on.

**The remediation is deliberately independent of the toggle.** If the Data API is off, RLS
is a second layer that costs nothing. If it is on, or is turned back on later, or the
project is restored to a new one, RLS is already there. A fix that only works while a
dashboard setting holds is a fix with an expiry nobody has diarised.

</honesty>
