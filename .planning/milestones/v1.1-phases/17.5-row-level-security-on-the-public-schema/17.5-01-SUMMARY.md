# Plan 17.5-01 — Summary

**Goal:** Every Postgres table the service creates denies every role but its owner, and
cannot silently stop doing so.

## What shipped

### Wave 1 — the DDL (`f818580`)

`ALTER TABLE … ENABLE ROW LEVEL SECURITY` appended to all four Postgres DDL sites:

| Site | Tables | Why it matters |
|---|---|---|
| `metrics.POSTGRES_SCHEMA` | `runs` | the daily spend cap's only input |
| `sessions.POSTGRES_SCHEMA` | `sessions` | question, answer text, owner identity |
| `limits.POSTGRES_SCHEMA` | `rate_hits`, `run_reservations` | guardrail state — a target, not a leak |
| `memory.PgVectorMemoryStore._ensure_schema` | `{self.table}` | the only configurable-name table |

The long-form rationale lives once, as a comment block in `metrics.py`; the other three
point at it rather than restating it.

### Wave 2 — the pins (`cbd7385`)

`tests/test_row_level_security.py`, four tests, two of them Postgres-gated.

**The structural gate discovers tables from the DDL itself.** A list of table names kept
beside the schemas would be a second source of truth, and the copy that drifts is the one
nobody runs — so a table added to a schema constant is picked up with no edit to the test.
It asserts a count first (`len(found) == 5`), because a regex that stopped matching would
otherwise sweep zero tables and report green.

**The behavioural gate reads the server's catalog**, because a statement can be present in
the source and still not have run — the structural gate cannot tell the difference.

**A separate test forbids `FORCE`.** That mutation is the one that fails *silently*: with
no policy defined, a forced table returns zero rows to its owner without raising, so
sessions would look empty rather than broken.

### Wave 3 — the operator half (`docs/OPERATIONS.md`)

A "Row level security" section stating the posture, the one-time `REVOKE` the application
cannot issue itself (`anon`/`authenticated` do not exist on a plain Postgres), and a
read-only pre-flight that prints table owner against the connecting role. Cross-referenced
from the embedding-migration procedure, since an operator following that runbook would not
otherwise read the Supabase section.

## Mutations observed red

Three probes, each red on the assertion that owns it:

| Probe | Result |
|---|---|
| Delete `ALTER TABLE run_reservations ENABLE ROW LEVEL SECURITY` from `limits.py` | **RED** — structural gate, on the "creates … without enabling row level security" message |
| Swap `ENABLE` → `FORCE` in `sessions.py` | **RED on both** — the ENABLE regex stops matching *and* the FORCE test fires |
| Remove the statement from `metrics.py` **and** run against a virgin database | **RED on the armed gate alone**: `runs exists on the server with RLS OFF` |

The third is the one that proves the two gates are not the same gate. Removing a statement
reds the structural test trivially; running it against a server that never received it is
the only way to show the behavioural test reads the catalog rather than the source.

## Deviations from the plan as conceived

- **The first draft of the fix was a SQL script for the operator to run.** It was replaced
  by schema-constant DDL after noticing `migrate.py embeddings re-embed --to` creates
  tables on demand: the script would have protected today's tables and missed tomorrow's.
  The script survives only as the `REVOKE` half, which genuinely cannot live in code.
- **Two internal-API guesses were wrong and were corrected by running the test, not by
  reading harder:** `Database.fetchall` returns dict rows rather than tuples (`KeyError: 0`),
  and `limits` has no module-level schema function — `PostgresLimits()` applies it in
  `__init__`. Both surfaced on the first armed run.
- **A stray `RLS_NOTE = __doc__` line** was written into `metrics.py` and removed in the
  same session before commit; it would have bound the module docstring to a misleading name.

## What this plan did not do

- No RLS **policies**. Row ownership is enforced in application queries (Phase 12); a
  second copy as policies is two rules that can disagree.
- No verification of the Data API's on/off state — see `17.5-CONTEXT.md` § honesty. The
  external probe cannot distinguish it, and the remediation is deliberately independent
  of it.
- No production deploy. The DDL lands on the next deploy, whichever way that now happens —
  the method is in transition (auto-deploy on push reported enabled 2026-08-12, but the
  merge of this phase's own PR #20 produced no release, so it is not yet demonstrated).
  Measured after that merge: `fly releases` still read **v12** from the previous day, and
  `/health` on the live service reported the pre-merge build. **RLS is not in production.**
