# Plan 10.5-05 — Documentation truth-up and the production cutover

## What shipped

**Task 1 — documentation (`fff0fbc`).** Four documents asserted the open session reads were
intentional; all four now describe what the code actually does.

- `docs/OPERATIONS.md` — `SESSIONS_TOKEN` row added (default *unset*, **fails closed**: 403 for
  everyone while unset). `DEMO_TOKEN` row amended to note it is accepted as a fallback. A new
  paragraph states the two are **not** interchangeable in production: setting `DEMO_TOKEN` 401s
  every anonymous visitor on `POST /research/stream` and takes the demo offline.
- `.env.example` — `# SESSIONS_TOKEN=` in the demo-guardrails block.
- `README.md` — API table marks the three session GETs and the DELETE as `X-Demo-Token`
  required (the DELETE was previously absent from the table entirely). The Limitations bullet
  lost only the sentence this phase fixed; the note eviction/dedup and session expiry/ownership
  gaps survive intact as Phase 12 work.
- `fly.toml` — comment only. No `[env]` change, no token value.

**Tasks 2 and 3 — the cutover.** The operator generated `SESSIONS_TOKEN` with
`openssl rand -hex 32` and staged it via `fly secrets set --stage`, so the secret and the code
landed in the same release. The 13 branch commits were fast-forwarded onto `main`, then a single
`fly deploy -a research-agent` ran from a clean `main`. That one cutover also carried Phase 10's
three pending commits (README restructure, `src/` reorganisation, its bugfix), eliminating the
deploy drift.

## Deviations

**Tasks 2 and 3 were run by the orchestrator, not this plan's executor.** The plan marks Task 3
`checkpoint:human-action gate="blocking-human"`, and the operator chose to generate and stage the
secret personally so its value never entered an agent's context. The executor ran Task 1 only and
was explicitly instructed not to invoke any state-mutating `fly` command.

**The plan's `never gated` acceptance grep cannot pass as literally written on macOS.** It filters
with `grep -v '^./.planning'`, but BSD `grep -rn … .` emits `.planning/…` without the `./` prefix,
so the filter never matches and the count came back 7. All seven hits are inside `.planning/`
(historical planning docs, correctly not rewritten retroactively). With `grep -v '^\.planning'`
the count is 0. The criterion is satisfied in substance. The same idiom appears elsewhere in the
plan and will recur on any re-run.

## Known gaps, deliberately left

- **`_index_json` in `service.py` does not advertise `DELETE /sessions/{id}`.** Wave 2 annotated
  the three GET entries; the DELETE was never in the index. The README table now lists it, but
  production code was left alone — this was a docs task, and
  `test_every_advertised_endpoint_actually_exists` only checks that advertised routes are served,
  not the converse. Worth a decision in a later phase rather than a silent fix here.
- **`ruff format --check` flags `tests/test_service.py`**, and did so before this phase began.
  The repo's gate is `ruff check`, which passes. Left for a separate formatting commit rather
  than burying the real diff in unrelated churn.
- **The token says *authorised*, not *who*.** Per-caller ownership, session expiry and note
  lifecycle remain Phase 12. Two orphaned notes from the sessions deleted on 2026-08-04 are still
  in the memory store.

## Requirement status

`REQ-live-endpoint-exposure` is now **Complete**. Waves 1–4 deliberately left it Pending because
its text reads "not reachable without credentials **on the deployed service**" — a claim no local
change could honestly satisfy. The v4 cutover and the anonymous 401s above are what satisfy it.
