# Phase 10.5 Plan 01: Fail-closed sessions credential Summary

**`limits.require_sessions_token` — a `SESSIONS_TOKEN` dependency that refuses everyone when no secret is configured, falls back to `DEMO_TOKEN`, and compares with `hmac.compare_digest`; nothing wired to it yet, by design.**

## Accomplishments

- `sessions_token()` reads `SESSIONS_TOKEN` per call and falls back to `demo_token()`, which is the mechanism that makes SC-2 ("setting `DEMO_TOKEN` protects the session endpoints") literally true rather than quietly false.
- `require_sessions_token()` raises `HTTPException(403, ...)` when nothing is configured — the fail-closed guarantee (T-10.5-01) and the one behaviour that stops this defect recurring on a deployment that forgets the secret.
- The `limits.py` module docstring no longer claims `/sessions` is never gated; it now draws the ops-read vs session-read distinction (`/health`, `/metrics`, `/pricing`, `/memory`, the demo page cost nothing; session reads return other people's research).
- Seven unit tests pin precedence, the fallback, fail-closed refusal, missing/wrong header (parametrised), and both acceptance paths. Every name contains `sessions_token`, so the `-k sessions_token` selector in the validation contract matches.

## Decisions Made

- **Header name is `x-demo-token`, reused.** CONTEXT left this to discretion. One header keeps the client-side story single: a caller that already knows how to authenticate to the demo needs no second concept.
- **Placement immediately after `check_token`.** The two functions differ in exactly one branch, and that branch is the defect. Adjacency makes the divergence legible to the next reader.
- **403/401 split** as RESEARCH § Pattern 1 specifies. 403 means "nobody can pass"; 401 means "you specifically did not".

### Requirement status — deliberately left Pending

The plan's frontmatter lists `requirements: [REQ-live-endpoint-exposure]`, and the standard
post-plan step marks those complete. I ran it, saw it flip the requirement to `[x]` / `Complete`,
and **reverted it**. The requirement reads "the session read and delete endpoints are not
reachable without credentials **on the deployed service**". This plan wired nothing and deployed
nothing — the exposure documented in STATE.md is still live and exploitable right now. Recording
it as satisfied would put a false claim about an open security hole into the project's own
tracking, which is the same class of error as the docstring this plan just corrected.

`REQ-live-endpoint-exposure` is phase-scoped across all five plans. It should be marked at the
plan-05 cutover, after the curl verification against the live host (SC-6), and not before.
