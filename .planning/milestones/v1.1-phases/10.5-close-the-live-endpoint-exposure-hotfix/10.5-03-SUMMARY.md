## Decisions Made

- **The daily-cap half is built the long way on purpose.** The fixture ships `DEMO_DAILY_USD_CAP=0` and `check_daily_cap` returns early for any cap `<= 0`, so the obvious construction — assert `GET /sessions` is 200 under fixture defaults — cannot fail even if the cap were wired onto the reads. The test drives a real `POST /research` to record spend, sets a positive-but-tiny cap, asserts `POST /research` now returns 429 to prove the cap is live, and only then asserts the reads. The `check_daily_cap` mutation above confirms the construction bites.
- **Create sessions before lowering the rate limit.** Session creation goes `POST /research` → `guard` → `check_rate_limit` and shares the DELETE's per-IP bucket. Lowering the limit first would let the setup requests consume the only slot: green for the wrong reason, and broken the moment anyone raises the limit.
- **`tracked_keys()` alone was not enough for the ordering test.** After `reset_limiter()` the count is 0, so `after == before` compares 0 to 0 and would hold even if the anonymous request had reached the limiter and been counted. The test therefore also asserts that an authorised `DELETE` still returns 204 with a limit of 1 — direct evidence the slot survived.
- **The refusal test is parametrised, not four near-identical functions**, matching the repo's existing `@pytest.mark.parametrize` convention at `test_unknown_sessions_are_404`.
- **`with TestClient(...)` for anonymous clients**, matching `test_unknown_sessions_are_401_without_a_token` from wave 2, so the lifespan runs the same way it does for the fixture's client.
