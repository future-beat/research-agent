## Accomplishments

- `sessions_router = APIRouter(prefix="/sessions", tags=["sessions"], dependencies=[Depends(limits.require_sessions_token)])` now owns `list_sessions`, `get_session`, `get_trace` and `delete_session`. The hole is closed in code (SC-1's code half).
- Grouping is by dependency, not path: the route-table walker confirms `POST /sessions/{session_id}/ask` and `.../ask/stream` still carry only `guard` and do **not** carry `require_sessions_token`. The demo's second turn is intact.
- `DELETE /sessions/{session_id}` carries `Depends(limits.check_rate_limit)` and nothing else extra (SC-3). Router dependencies run first, so an unauthorised caller is refused before it can burn a slot. `grep -c 'Depends(limits.check_rate_limit)'` returns exactly 1 — reads stay unmetered, and the daily cap's "Read-only endpoints still work" message stays true.
- `guard`'s docstring no longer over-claims. It now separates ops reads (`/health`, `/ready`, `/metrics`, `/pricing`, `/memory`, `/demo`) from session reads, and says why `guard` is deliberately *not* what closes the latter.
- The SSE error handler applies `_redact(first_line)[:160]`, the exact treatment `/health` already gives a probe failure (SC-4). No second regex — `_URL_CREDENTIALS` still has exactly 2 occurrences.
- The suite is green with a fixture-shaped diff: `grep -c 'x-demo-token' tests/test_service.py` returns 2 (the fixture default plus nothing sprinkled), and no `conftest.py` was added.

## Decisions Made

- **Router, not per-route dependencies.** CONTEXT left this to discretion. The defect's shape decided it: four routes each independently forgot a credential, so a control you must remember to repeat is one that will be forgotten again. A future `@sessions_router.get("/{id}/notes")` is guarded by construction.
- **One rate-limit bucket, shared with research runs.** A second module global would need a second entry in `reset_limiter()` and a second thing to remember in tests, for no behavioural gain at this scale.
- **The `/sessions` path has no trailing slash.** `@sessions_router.get("")` under `prefix="/sessions"` produces exactly `/sessions`, confirmed by the walker's output.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `test_every_advertised_endpoint_actually_exists` broke in two independent ways**
- **Found during:** Task 2
- **Issue:** The test parsed each index entry as exactly `"METHOD path"`, so the new ` (X-Demo-Token required)` annotation broke the split. More seriously, it built its `served` set with a *flat* scan of `app.routes` — which, under fastapi 0.141.1, no longer contains the routes of an included router at all. Left alone it would have passed vacuously over an index advertising three routes the scan could not see, which is exactly the failure mode CONTEXT § Structural regression test warns about.
- **Fix:** Added a `_served_routes()` helper that descends into `_IncludedRouter` via `original_router.routes` and `include_context.prefix`, plus a non-vacuity assertion (`("GET", "/health") in served`); parse the advertised string with `.split(" ")[:2]` so a trailing annotation is tolerated.
- **Files modified:** `tests/test_service.py`
- **Commit:** `e2596cd`

**2. [Rule 1 - Bug] `test_the_healthcheck_path_is_served` raised `AttributeError`**
- **Found during:** Task 2 (surfaced by the full-suite run, not the module run)
- **Issue:** `{route.path for route in service.app.routes}` — the `_IncludedRouter` object in `app.routes` has no `.path`.
- **Fix:** `getattr(route, "path", None)`, with a comment noting the healthchecks all target top-level ops routes so no descent is needed.
- **Files modified:** `tests/test_deploy_config.py`
- **Commit:** `e2596cd`

Both are the same root cause and are worth flagging to plan 04: **any** existing or future assertion over `app.routes` is now wrong unless it is recursive. Plan 04's structural regression test already plans for this; these two were pre-existing sites that did not.

The plan's own acceptance criteria did not anticipate `tests/test_deploy_config.py` being touched, which is why the file appears in this summary's `key-files` but not the plan's `files_modified`.
