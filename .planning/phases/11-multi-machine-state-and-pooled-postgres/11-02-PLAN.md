  <action>
    **The deadline is the substance of this task.** `PG_POOL_TIMEOUT` bounds a *checkout*, not the
    statement that follows it. RESEARCH's timing table is scoped to "database unreachable, pool
    empty" and never considers the warm-pool partition: the pool holds a connection that still looks
    live, the checkout returns in ~0 ms, and then `store.count()` blocks on a socket to a peer that
    has gone away. `connect_timeout` does not apply to an established connection. Plan 11-01 adds
    `statement_timeout` and `tcp_user_timeout`, which cover a slow server and a peer that stops
    ACKing — but a peer that keeps the socket alive and simply never answers is bounded by nothing in
    libpq. Left there, `/health` can exceed Fly's 15 s check timeout, Fly restarts both machines, and
    the phase reintroduces exactly the restart loop `/health` was split from `/ready` to prevent —
    now reachable because the database moved across a provider boundary.

    Add `health_probe_budget() -> float` to `service.py` beside the other env readers: reads
    `HEALTH_PROBE_BUDGET`, default `3.0`, floor `0.1`. Change `_probe(fn)` to run `fn` in a worker
    thread (a module-level `ThreadPoolExecutor(max_workers=3, thread_name_prefix="health-probe")` is
    enough) and take `future.result(timeout=health_probe_budget())`. On
    `concurrent.futures.TimeoutError`, return the existing failure shape with
    `{"reachable": False, "error": "TimeoutError", "detail": "probe exceeded Ns"}`. The abandoned
    worker is left to finish on its own — it is reaped when `tcp_user_timeout` or the keepalive
    sequence fires, and a bounded number of them can be outstanding because the executor is bounded.
    Say all of that in the docstring, including the bit that is a tradeoff rather than a win.

    Write the arithmetic in the docstring as a **ceiling**, not as a typical case: three sequential
    probes × `HEALTH_PROBE_BUDGET` (3.0 s) = **9 s guaranteed**, inside Fly's 15 s check timeout,
    regardless of whether the pool was cold, warm, or partitioned. The ordinary cold-pool case is
    3 × `PG_POOL_TIMEOUT` = ~6 s and is not the bound. State that the pre-pool code had no ceiling at
    all in the warm case and up to 18 s in the cold one (two 3 s connect attempts per probe, three
    probes, against a 15 s timeout) — so this is a defect the phase **fixes**, not one it inherits.

    In `lifespan`'s `finally`, after the two existing `close()` calls, call `db.close_all_pools()`.
    `graph.memory()` holds a third `Database` that nothing ever closes, so without this a shutdown
    leaves a pool and its background workers alive. Import `db` at module scope alongside the other
    `research_agent` imports; it is already an in-process module with no import-time I/O. Shut the
    probe executor down here too, with `cancel_futures=True` and no wait.

    Add `FLY_MACHINE_ID` to the `/health` body as a top-level `"machine"` key, reading
    `os.environ.get("FLY_MACHINE_ID", "")` — empty string when running off Fly, never absent, so the
    response shape is stable in tests. This is what makes SC-3 demonstrable in two `curl`s instead
    of by reading `fly logs`: today nothing in any response says which machine answered.

    Do not change `_dependencies`'s three-probe shape or the 200-with-degraded-body contract. A
    `PoolTimeout` must keep surfacing as `reachable: false` with a redacted detail, not as a 500.
    `/ready` keeps returning 503.

    In `tests/test_service.py`, add:
      - **The deadline test, named so `-k health_probe_deadline` selects it.** Use a fake store whose
        `count()` sleeps far longer than the budget (e.g. 30 s) — a deterministic hang, no network
        involved, so it exercises the warm-pool-partition shape rather than the cold one. Set
        `HEALTH_PROBE_BUDGET` small (e.g. `0.3`), call `/health`, and assert: status 200, that store

      - A test that `/health` carries a `machine` key, that it echoes `FLY_MACHINE_ID` when set, and

      - A test that a pool error surfaced through `/health` carries no password: set an unreachable

  <action>
    Add six Postgres-gated tests to `tests/test_store_contract.py`. Every one uses the existing
    `@pytest.mark.skipif(not HAS_POSTGRES, ...)` idiom so it skips cleanly without `DATABASE_URL` and
    runs for real in CI. **Do not add a `conftest.py`** — this repo has none by convention; shared
    fakes live in the owning module and are resolved via `pythonpath = [".", "src", "tests"]`.

    1. **`advisory_lock_is_exclusive`** — the falsifying gate for plan 11-01's single-connection
       invariant, and the reason the string greps on `pg_advisory_lock` are not evidence. Open
       connection A through a `Database` and hold `SELECT pg_advisory_lock(db.SCHEMA_LOCK_KEY)` open
       on it. From a **separate** connection B, assert `SELECT pg_try_advisory_lock(db.SCHEMA_LOCK_KEY)`
       returns **`False`**. Release on A and assert `pg_advisory_unlock` returned **`True`** — a
       `False` there means the lock was taken on a different connection than the unlock, which is the
       exact no-op-plus-leak failure the plan exists to prevent. Then assert B can take it.
       This test must fail if `_apply_schema` ever splits its lock/DDL/unlock across `cursor()` calls;
       state that in the docstring.

    2. **`concurrent_schema_init`** — construct two `Database` objects on the same DSN against a
       schema that has been dropped first, and drive `_apply_schema` from two threads started at the
       same barrier. Both must return without raising and both must end with `schema_applied` True.
       **This is a regression test, not a lock test** — `CREATE ... IF NOT EXISTS` plus the
       duplicate-object tolerance satisfies it with the lock entirely absent. Say so in the docstring
       and point at `advisory_lock_is_exclusive` as the test that actually proves the lock. It still
       earns its place: it is the two-machines-booting-against-an-empty-database race, which was
       structurally impossible to hit before this phase because only one process ever ran the lazy
       schema path.

    3. **`statement_timeout_bounds_a_slow_query`** — set `PG_STATEMENT_TIMEOUT` to a small value
       (e.g. 500 ms) on a **test-unique** DSN, run `SELECT pg_sleep(5)` through a `Database`, and
       assert it raises `psycopg.errors.QueryCanceled` in well under 5 s. This is the falsifying gate
       for the server-side half of the post-checkout bound; without the `options="-c statement_timeout=..."`
       kwarg it hangs for the full five seconds and fails. Note in the docstring what it does **not**
       cover: a peer that stops answering entirely, where the server-side cancellation never reaches
       the client — that case is bounded by `/health`'s per-probe deadline, tested in Task 1.

    4. **`pgvector_search_path`** — assert the pool's `configure` callback took effect: open a
       connection through a `Database` and read back `SHOW search_path`, asserting `extensions`
       appears in it. Then exercise an actual `%s::vector` cast through `PgVectorMemoryStore` on the
       contract table with the 5-dimensional `FakeEmbedder`, proving the cast resolves rather than
       merely that a setting is set. Supabase installs the extension into `extensions`; CI's image
       does not have that schema at all, and Postgres tolerates missing schemas in `search_path`, so
       the test must pass in both worlds.

    5. **`cross_instance` session resolution** — write a session through one `PostgresSessionStore`
       and read it back through a **separately constructed** `PostgresSessionStore` on the same DSN,
       asserting identical content. This is the actual mechanism SC-3 depends on. A second machine
       adds a network boundary and a Fly routing decision; it does not add a new code path. Say so in
       the docstring, and say what it does *not* prove — that the proxy routes to two machines, which
       is verified live in plan 11-05.

    6. **`concurrent`** — drive N threads (N comfortably above `PG_POOL_MAX_SIZE`, e.g. 12 against a
       max of 5) through `store.count()` simultaneously; assert every thread succeeds and none raises
       `PoolTimeout`. Before this phase all N would have queued behind one lock-guarded connection.

    Any test that varies pool env vars must use a **test-unique DSN** and must dispose its pools in a
    `finally` (or via `db.close_all_pools()`), for the same registry-caching reason documented in
    plan 11-01 Task 3.

    These tests raise the local skip count. That is expected and legitimate — see the note in
    `<verification>`. What must never happen is a test that skips **under `REQUIRE_POSTGRES`**, which
    would undermine `test_postgres_really_ran_when_ci_said_it_would`.
  </action>
