<objective>
Remove per-machine state from the topology, make the Postgres backends mandatory, scale to two
machines, and prove the phase's headline claim live.

Purpose: SC-2 and SC-3. This is the point of no return for per-machine state — everything up to
here was reversible by `fly secrets unset DATABASE_URL`, and from here the machines hold no local
store. That is safe only because plan 11-04 already proved the database reachable from production.

Output: a two-machine stateless fleet that fails closed rather than silently falling back, the
evidence that a session created against one machine resolves from the other — recorded as two
distinct machine IDs, not asserted — and a `11-VALIDATION.md` that says what actually happened.

**Never destroy the volume.** `agent_data` is kept as the backup. Detaching is reversible;
destroying is not. `fly volumes destroy` does not appear anywhere in this phase and must not be run.
</objective>

    The pins are the load-bearing half, and they are not optional. Removing the three `*_DB_PATH`
    vars on its own does **not** prevent the SQLite fallback this phase exists to end:
    `sessions.py:43` defaults `SESSION_DB_PATH` to a path next to the module, and `default_backend()`
    returns `"sqlite"` whenever `db.postgres_configured()` is false. So with `DATABASE_URL` unset or
    empty, two mount-less machines each boot on their own container-local SQLite file — per-machine
    split-brain again, now with data that vanishes on restart, and invisible to every automated
    consumer: `/health` reports `dependencies: "ok"` because SQLite is perfectly reachable, Fly's
    check passes, and the only difference is a backend class name nothing reads.

    With the pins, the same situation **fails closed**: `get_session_store()` resolves to
    `PostgresSessionStore`, which calls `db.database_url()`, which raises `RuntimeError` naming
    `DATABASE_URL`. The store never constructs, `lifespan` raises, and the app does not come up.
    That is the intended behaviour for a configuration error — loud beats quiet, and a restart does
    not fix a missing secret either way. Note the distinction in a comment above the pins so it is
    not mistaken for belt-and-braces: an *outage* (DSN present, server unreachable) still comes up
    degraded, because `Database.__init__` does no I/O; only an *absent DSN* fails closed. Plan
    11-02's `-k fails_closed` tests assert the raise; plan 11-03's stateless guard arm asserts the
    pins are present in this file.

    Do not change `auto_stop_machines = 'suspend'` — it stays, and it is what bounds idle cost.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → `/sessions/{id}` | The session read tree is closed by `SESSIONS_TOKEN` and fails closed while it is unset |
| Fly proxy → either machine | Routing is now non-deterministic; correctness can no longer rely on which machine answers |
| operator → irreversible Fly commands | `fly volumes destroy` sits one word away from `fly volumes list` |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

The actual mitigation is Task 1's three backend pins, which make `db.database_url()` raise at store construction when the DSN is absent. Asserted three ways: 11-02's `-k fails_closed` unit tests, 11-03's stateless guard arm requiring the pins in `fly.toml`, and Task 1's fail-closed spot check. **Residual, accepted:** an absent DSN now prevents the app from booting rather than degrading it. | T-11-24 | Denial of service | connection exhaustion after doubling the fleet | mitigate | 2 × `max_size` 5 = 10 of Nano's 60; Task 2 re-checks `pg_stat_activity` after the scale rather than trusting the arithmetic |

Documented in OPERATIONS by plan 11-03 and owned by Phase 12's `REQ-store-lifecycle-and-ownership` |
