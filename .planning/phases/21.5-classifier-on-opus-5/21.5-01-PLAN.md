are settled here as locked implementation. The executor implements them as written.

**P-01 — The mechanism: `CLASSIFIER_MODEL` env knob, default `"claude-opus-5"` DIRECTLY.**
Not `MODEL`. The trap 21.5-CONTEXT names is real and researched: `critic_model()`'s
neutral default was correct for Phase 16 because that capability was opt-in; this phase's
requirement IS the opt-in, already made by the user at milestone level. A `MODEL` default
would make every unconfigured shell — CI, a fresh checkout, and the operator's shell
during 21.5-03's re-record — classify on Sonnet, reproducing the exact failure this phase
exists to fix. The knob exists only for the emergency downgrade (an Opus outage, a future
deprecation), read fresh on every call, no validation past strip-or-default (the
`critic_model()` shape, opposite polarity, and the docstring says so).

**P-02 — Fixture provenance is recorded and deliberately NOT compared.**
`record_case_to_fixture` writes `"classifier": graph.classifier_model()` as a fourth,
EXTRA role; `REQUIRED_MODEL_ROLES` stays `("pipeline", "judge")`; `grade_fixture_current`
gains no classifier arm. The precondition that keeps the critic's staleness gate harmless
in CI — a neutral code default — does not hold here: `classifier_model()` returns
`claude-opus-5` in EVERY environment from the moment this plan merges, so a comparison
(backfilling absent keys to the pipeline model, Sonnet) would grade all 19 committed
fixtures stale in CI on every push. Task 2 demonstrates that cascade by temporary
mutation, observes the 19 reds, reverts, and records it — the honest argument the ADR
(21.5-02) carries.

**P-03 — The probe is a committed tool under `evals/`, and the prompt is factored, not
copied.** `evals/classifier_probe.py`, runnable as `python -m evals.classifier_probe`,
following `evals/__main__.py`'s preview-before-client, `--yes`-to-spend idiom. The
classifier's inline f-string prompt moves to a module constant
`graph.CLASSIFIER_PROMPT_TEMPLATE` (safe: nothing in the tree pins the prompt's wording
except `ScriptedClient`'s dispatch on the literal `"Respond with exactly one word"`, which
the constant preserves and a test now pins). The probe imports the constant, so the
measurement can never drift from the shipped classifier. One variable: the prompt's TEXT
does not change in this move — byte-identical relocation only.

**P-04 — `fly.toml` carries the line; the deploy test pins the VALUE with an inverted
fail-direction.** `CLASSIFIER_MODEL = 'claude-opus-5'` lands beside `CRITIC_MODEL` so the
per-node model stance is readable in one place. Unlike `CRITIC_MODEL`, DELETING this line
changes nothing — the code default is the same model, so absence fails safe and the test
must not red on it. What IS dangerous is drift: the knob is honored, so a line carrying a
DIFFERENT value silently moves production off the measured choice. The pin therefore
asserts `env.get("CLASSIFIER_MODEL") in (None, "claude-opus-5")` — absence legal, wrong
value red — and its docstring states why the direction is inverted from the
`CRITIC_MODEL_PIN` above it.

**P-05 — The three-way label split, exactly as researched — and `general-defines-a-term`
is RELABELLED (research Open Question 2, resolved toward correction).**
`followup-with-no-prior-research` and `injection-tries-to-force-approval` relabel to
`technical` in `expect_topic_type`/`topic_label` LOCKSTEP (moving only one field breaks
the offline leg: ScriptedClient replays `topic_label`, and a stale `general` there is a
valid RESEARCH_STRATEGY key that never falls back) — their `why` never depended on
generalness, so the relabel is pure metadata. `general-defines-a-term` relabels the same
way WITH reasoning appended to its `why`: two models independently read its
HTTP-idempotency content as technical, the label was wrong, and the default path stays
covered by `general-summary`, `general-explains-a-concept` and
`general-how-a-mechanism-works`. `chatty-label-falls-back` is NOT TOUCHED in any label
field: it is one of exactly three cases holding
`test_dataset_taxonomy_per_stratum_minimums`' off-menu-general `>= 3` floor (zero spare),
and its conflict is structural — the offline leg needs `general` unconditionally (it
exercises the fallback), the live leg computes `technical` on any competent model — so it
gets the leave-and-document resolution, appended to its `why`. Post-resolution arithmetic,
a claim to check: `general` count 11 → 8 (floor 7), off-menu count unchanged at 3. Pins,
notes, reports stay untouched on all four cases — the fence is lifted for labels/tasks
only.

**P-06 — This phase takes ADR-0013, slug `classifier-on-its-own-model`.** Phase 22's
