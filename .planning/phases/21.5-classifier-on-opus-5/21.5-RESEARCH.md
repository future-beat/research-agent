**Researched:** 2026-08-16

## Summary

This phase has one real design decision (the classifier's model mechanism) and it has a trap
CONTEXT.md names explicitly: mirroring `CRITIC_MODEL`'s "neutral default, `fly.toml` pins
production" shape would make every keyless and local-shell invocation of the classifier —
**including this phase's own re-record checkpoint** — run on Sonnet, reproducing exactly the
failure the phase exists to fix. The fix is to break the symmetry deliberately: a
`CLASSIFIER_MODEL` knob whose **default is `claude-opus-5`**, not `MODEL`. That single choice
then cascades into every other question this research was asked: it means **no**
`grade_fixture_current` staleness gate should be added for the classifier role (adding one, the
way Phase 16 did for the critic, would retroactively stale all 19 already-recorded fixtures the
moment this phase merges — the critic's staleness gate only stayed harmless in CI because
`CRITIC_MODEL`'s default is neutral, and that precondition does not hold here). It means the
existing smoke-test assertions that pin `models["classifier"] == graph.MODEL`
(`tests/test_graph_smoke.py:799,817,978`) go red on implementation and must be rewritten as part
of the phase, not treated as incidental breakage.

Of the four disputed labels, the research finds the group is **not uniform**: two
(`followup-with-no-prior-research`, `injection-tries-to-force-approval`) can be safely relabeled
`technical` because their `why` never depended on generalness and the label is pure metadata (no
notes/report edit needed). One (`general-defines-a-term`) is genuinely mislabeled but its notes
and report are HTTP-technical prose that the "pins, notes, reports stay" house constraint
forbids touching — so **rewording its task is not a safe option** here, and the honest move is
relabel-with-a-note, accepted at a real but small stratum-count cost. The fourth
(`chatty-label-falls-back`) **must not be touched at all**: `tests/test_evals.py:148-163`
(`test_dataset_taxonomy_per_stratum_minimums`) pins `>= 3` cases whose offline `topic_label` is
off-menu AND whose `expect_topic_type` is `general` — and this case is one of exactly three that
satisfy it today. Relabeling it reds that gate on a floor with zero spare cases; it is a
structural conflict (its offline fallback path and its live/recorded classification path want
different answers, and no model choice resolves that) with only one safe resolution: leave it,
and document why.

Re-deriving the "six" `topic_type`-refused cases from `evals/REFUSALS.json`'s literal `detail`
strings finds **eight**, not six — the believed list in CONTEXT.md missed
`followup-with-no-prior-research` and `followups-chain-of-three`. Three of the eight carry a
second, unrelated grader failure alongside `topic_type` and are predicted to refuse again for
that second reason regardless of what this phase does — one of those (`judge_followup_honesty`
firing on a turn a budget guardrail correctly stopped before any draft existed) looks like a
latent grader defect out of this phase's scope to fix.

**Primary recommendation:** `graph.classifier_model()` defaults to `"claude-opus-5"` (not
`MODEL`), threaded through `call_model`'s existing per-node seam exactly like `critic_model()`;
record it as an *additive, non-gating* `models.classifier` fixture field (provenance only, no
staleness comparison); relabel `followup-with-no-prior-research`,
`injection-tries-to-force-approval`, and `general-defines-a-term` to `technical`; leave
`chatty-label-falls-back` untouched and document the structural reason; re-derive the refusal
list as eight cases, not six, before quoting the re-record checkpoint.

## Q1 — The mechanism, and closing the trap

### How `call_model` resolves a node's model today

`call_model(state, node, *, model=None, **kwargs)` [VERIFIED: src/research_agent/graph.py:116-163]
resolves `model = model or MODEL` once, then uses that resolved name at **four** sites: the
`span`, the API call, `usage_accounting.record(...)`, and the log line. Every node but the
critic calls it with no `model=` kwarg and gets `MODEL` (`"claude-sonnet-5"`)
[VERIFIED: src/research_agent/graph.py:45]. The critic is the one exception:

```python
# src/research_agent/graph.py:521 (critic_node)
response = call_model(
    state, "critic", model=critic_model(), max_tokens=2000, ...
)
```

`critic_model()` [VERIFIED: src/research_agent/graph.py:61-78] is:

```python
def critic_model() -> str:
    return os.environ.get("CRITIC_MODEL", "").strip() or MODEL
```

— read fresh on every call (no module-scope caching, explicitly documented as the
`sessions_token()` idiom so an operator changing config mid-process takes effect and tests can
`monkeypatch.setenv` it). `classifier_node` [VERIFIED: src/research_agent/graph.py:287-312]
calls `call_model` with no `model=` kwarg at all today, so it always runs `MODEL` (Sonnet).

### The trap, closed

CONTEXT.md's trap: if a new `CLASSIFIER_MODEL` knob follows `critic_model()`'s exact shape
(unset → `MODEL`), then any shell that does not explicitly export `CLASSIFIER_MODEL=claude-opus-5`
— including the operator's own shell during **this phase's own re-record checkpoint** — runs the
classifier on Sonnet. That reproduces the underlying cause of the topic-type refusals Phase 21
hit, inside the very phase meant to fix them.

**Recommendation: `classifier_model()` defaults to `"claude-opus-5"`, not `MODEL`.**

```python
def classifier_model() -> str:
    """The model the classifier runs on. Unlike `critic_model()`, the neutral
    default here is claude-opus-5, not MODEL -- because the classifier's Opus
    upgrade is not an opt-in capability an operator turns on, it is the shipped
    default this phase's own measurement settled. A knob still exists for the
    emergency downgrade (an Opus outage, a future deprecation), read fresh on
    every call for the same reason critic_model() is.
    """
    return os.environ.get("CLASSIFIER_MODEL", "").strip() or "claude-opus-5"
```

This closes the trap structurally: a shell with `CLASSIFIER_MODEL` unset — the operator's laptop
during the re-record, CI, a fresh checkout — gets Opus 5 with zero configuration. The knob exists
only for the downgrade direction (an operator explicitly setting `CLASSIFIER_MODEL=claude-sonnet-5`
or similar), which is the opposite polarity of `CRITIC_MODEL`'s knob (there, unset is the weak
default and setting it is the upgrade).

**Consequence for the P-06 env assertion (21-RECORD-RUNBOOK.md's pattern):** the existing
assertion pattern requires `CRITIC_MODEL` and `EVAL_JUDGE_MODEL` to be **unset**
[VERIFIED: .planning/phases/21-forty-recorded-answers/21-RECORD-RUNBOOK.md:73,75,90-101]
("poison = must be unset"). `CLASSIFIER_MODEL` cannot join that "must be unset" list — unset is
now the *correct* state (it resolves to Opus 5), not a poison state. The re-record runbook's
assertion for this phase must instead assert `CLASSIFIER_MODEL` is **either unset, or explicitly
set to `"claude-opus-5"`** — never silently accept an unset variable meaning something different
than intended, and never accept it set to anything else without the operator knowing why.

### Does pricing "just work"?

Yes, with zero code changes. `usage.PRICES` already carries a `claude-opus-5` row
(`$5/$25/$6.25/$0.50`) [VERIFIED: src/research_agent/usage.py:96-98] — the same row the critic
already uses in production. `call_model` passes the resolved `model` string into
`usage_accounting.record(state["usage"], call, model)` [VERIFIED: src/research_agent/graph.py:145],
and `record()` prices by that string via `price_for(model, on)` [VERIFIED: src/research_agent/usage.py:404-417].
Nothing caches a model name anywhere in this path — `critic_model()`'s docstring calls this out
explicitly as deliberate, and the same is true of `call_model`'s `model` parameter (resolved once
per call, never at import). A `classifier_model()` accessor following the same shape needs no
`usage.py` changes at all.

### Is this symmetric with the CRITIC_MODEL / ADR-0010 precedent?

**Deliberately not fully symmetric**, and the ADR should say so in its own voice. Phase 16's
neutral default existed because shipping the *capability* was meant to change nothing until an
operator opted in [VERIFIED: .planning/milestones/v1.1-phases/16-independent-critic-model/16-CONTEXT.md:29-34].
This phase's mandate is the opposite: REQ-classifier-model *is* the opt-in, already made by the
user, at milestone-requirement level — there is no "ship the capability, decide later" step to
protect. An ADR that copied CRITIC_MODEL's shape verbatim would misrepresent why the default
direction differs.

## Q2 — Fixture provenance, and why NOT to add a staleness gate

### What `write_fixture` records today

`record_case_to_fixture` [VERIFIED: evals/harness.py:566-583] builds `models` as:

```python
models={
    "pipeline": graph.MODEL,
    "judge": judge.model,
    "critic": graph.critic_model(),
}
```

`fixtures.py`'s `REQUIRED_MODEL_ROLES = ("pipeline", "judge")` [VERIFIED: evals/fixtures.py:53-56]
— `critic` is an *extra* role, present in every fixture recorded since Phase 16 but never
required by `_validate_models` [VERIFIED: evals/fixtures.py:269-280]. This is the exact
precedent to extend: add `"classifier": graph.classifier_model()` as another extra role, never
added to `REQUIRED_MODEL_ROLES`.

### What `grade_fixture_current` compares — and the reason NOT to extend it

`grade_fixture_current` [VERIFIED: evals/harness.py:353-425] compares exactly two roles:
`models.pipeline` against `graph.MODEL`, and `models.get("critic") or recorded` (backfilled to
`pipeline` for pre-Phase-16 fixtures) against `graph.critic_model()`. It explicitly documents
*why* this stays safe in CI: `CRITIC_MODEL`'s code default is neutral, so `critic_model() == MODEL`
in every keyless/CI context regardless of the phase's cutover, and only a shell that has
`CRITIC_MODEL` explicitly set (production, or an operator's deliberate override) sees staleness.

**This precondition breaks for the classifier under the Q1 recommendation.** If
`classifier_model()` defaults to `"claude-opus-5"` unconditionally, then `graph.classifier_model()`
returns `"claude-opus-5"` in **every** environment, including CI, the moment this phase ships —
not just where an operator opts in. If `grade_fixture_current` grew a parallel classifier
comparison (`models.get("classifier") or recorded` vs. `current_classifier`), all **19**
already-recorded fixtures (none of which carry a `classifier` key, since it didn't exist when
they were recorded, and whose backfill would resolve to `graph.MODEL` = `claude-sonnet-5`) would
grade **stale in CI, on every push**, from the moment this phase merges — not just the 6–8 cases
this phase is scoped to re-record. That is a scope explosion CONTEXT.md never asked for (it
scopes the re-record to the `topic_type`-refused cases specifically), and it would turn a green
suite red for 19 cases this phase has no budget to fix.

**Recommendation: record `models.classifier` for honest provenance; do NOT add a staleness
comparison for it in `grade_fixture_current`.** A human or a future phase reading a fixture file
can see which model classified it; CI's green/red state is unaffected by which model the
classifier happens to run on for any given committed recording. This is the one place this
phase's design should NOT mirror Phase 16's shape, and the reasoning above is exactly the
argument the ADR needs to carry, because a reader familiar with `critic_model()`'s precedent will
otherwise expect a parallel gate and wonder why one is missing.

### Additive-only constraint, verified

19 existing fixtures lack a `models.classifier` key. `_validate_models`
[VERIFIED: evals/fixtures.py:269-280] only requires `REQUIRED_MODEL_ROLES = ("pipeline", "judge")`
and explicitly documents "extra roles are kept verbatim" — so adding `classifier` as a new,
optional, extra key is safe under the existing loader with zero code change to
`fixtures.py`'s validation. `stale_judges()` [VERIFIED: tests/test_evals.py:2425-2453] only reads
`models["judge"]`; unaffected. Nothing in `evals/graders.py`'s `RECORDED_GRADERS` reads a
`classifier` key. The union gate
(`test_every_golden_case_is_recorded_or_documented_as_refused`) reads only fixture *filenames*,
not `models` contents. No consumer of the additive field breaks.

## Q3 — The probe as a committed artifact

### Location and shape

Recommend a new module `evals/classifier_probe.py`, runnable as `python -m evals.classifier_probe`,
sibling to `evals/__main__.py` rather than a flag bolted onto it — the probe's shape (two models,
one prompt, no full graph invocation, no judge, no fixture write) is different enough from
record/replay/live that folding it into the existing argparse surface would blur what `--record`
and `--live` mean. It should follow the SAME `--yes`-gated, quote-before-spend idiom already
proven in `evals/__main__.py:499-519` (`record_preview` printed, client never built until `--yes`).

### Reuse the graph's actual prompt — do not duplicate it

`classifier_node`'s prompt is inlined in an f-string
[VERIFIED: src/research_agent/graph.py:296-306] — quoted verbatim:

```
f"Classify this research task into exactly one category: "
f"technical, contested, sparse, or general.\n\n"
f"technical = involves specific figures/versions/technical facts\n"
f"contested = involves differing opinions or disputed claims\n"
f"sparse = likely has limited web coverage (niche/local/very recent)\n"
f"general = none of the above apply strongly\n\n"
f"Task: {state['task']}\n\n"
f"Respond with exactly one word: technical, contested, sparse, or general."
```

`evals/harness.py:133`'s `ScriptedClient.create` dispatches on the literal substring
`"Respond with exactly one word" in prompt` [VERIFIED: evals/harness.py:130-154] to decide a call
is the classifier's. No test anywhere pins the *rest* of the prompt's wording — a grep across
`tests/*.py` and `evals/*.py` for `"technical, contested, sparse, or general"` and `"Classify this
research task"` returns nothing. **The prompt can safely be factored into a module-level
constant** (e.g. `graph.CLASSIFIER_PROMPT_TEMPLATE`, formatted with `task=`) as long as the
extracted text still contains the literal substring `"Respond with exactly one word"` verbatim —
that substring is the only thing anything else in the tree depends on. The probe script should
import and reuse that constant rather than re-typing the prompt, so drift between the probe and
the shipped classifier is structurally impossible.

### What it measures, cost, and where results land

Filter `evals.dataset.GOLDEN` to `case.expect_topic_type is not None` — verified as exactly 38
cases by direct enumeration of `dataset.py` [VERIFIED: evals/dataset.py:194-1001, all 40 `Case`
entries counted by hand against their `expect_topic_type` field], matching REQUIREMENTS.md's
stated "all 38 golden cases carrying an expect_topic_type." For each case, call BOTH
`claude-sonnet-5` and `claude-opus-5` with the identical formatted prompt (`max_tokens=20,
thinking={"type":"disabled"}, output_config={"effort":"medium"}` — the exact kwargs
`classifier_node` uses, so the probe measures the real call shape, not an approximation), compare
each model's returned label to `case.expect_topic_type`, and compute:

- per-case per-model pass/fail
- a **regressions** list: cases where Sonnet matched and Opus did not (must be empty to trust the
  switch, per the locked decision)
- summary counts matching the requirement's stated shape (`34/38` vs `29/38`)

76 total classifier calls (38 cases × 2 models), ~140 input / ~5 output tokens each per
CONTEXT.md's own measured figures — the 2026-08-15 run cost $0.053
[CITED: .planning/phases/21.5-classifier-on-opus-5/21.5-CONTEXT.md:18-22, a project record this
session opened directly]; a repeat run at execution should cost similarly, re-quoted at run time
per the locked decision (no trusted number is reused). This is materially cheaper and structurally
different from the re-record checkpoint (Q5): the probe never invokes the full graph, never calls
a judge, and never writes a fixture — it isolates the classifier call alone.

**Results land in the phase directory**, not the scratchpad: CONTEXT.md is explicit that the
2026-08-15 session's numbers (archived to a scratchpad path) are not trusted going forward and
the probe is re-run. Recommend
`.planning/phases/21.5-classifier-on-opus-5/classifier-probe-report.json`, committed to git as the
Manual-Only evidence artifact this phase's Validation Architecture cites.

### `chatty-label-falls-back` — leave the label; document the structural conflict

**Why:** its `expect_topic_type` is asked to serve two grading paths that want different answers,
and no model choice changes that.

- **Offline (CI, keyless):** `ScriptedClient` always returns `case.topic_label` regardless of the
  real task content [VERIFIED: evals/harness.py:130-154]. Since the scripted label ("Well, it's
  sort of technical...") is not a valid key in `RESEARCH_STRATEGY`
  [VERIFIED: src/research_agent/graph.py:265-273], `classifier_node`'s fallback fires
  unconditionally: `state["topic_type"] = label if label in RESEARCH_STRATEGY else "general"`
  [VERIFIED: src/research_agent/graph.py:310]. This branch is exercised **regardless of which
  live model exists** — it is pure offline scripting.
- **Live/recorded:** the task ("Explain how a Kalman filter combines noisy measurements over
  time.") reads as genuinely technical content. A real, working classifier — Sonnet or Opus —
  returns a clean one-word `"technical"`, never chatty prose (chattiness is not something either
  model naturally does on this well-formed a prompt). So the live/recorded leg's `topic_type`
  grader compares a real `"technical"` against `expect_topic_type="general"` and fails, **on
  either model** — this is exactly why the case appears in `REFUSALS.json` under `kind:
  "judge_truncated"` rather than being resolved by Phase 21's original attempt, and it explains
  why the probe (which queries live models directly) found both Sonnet and Opus disagreeing with
  the dataset here.

**Rewording is blocked, not just undesirable.** The house constraint freezes `notes`/`report`;
`chatty-label-falls-back`'s notes and report are Kalman-filter-specific prose. Rewording the task
away from Kalman filters to a genuinely general topic (which would resolve the live-side conflict
cleanly) would leave the notes/report topically orphaned — exactly the kind of authored-content
mismatch the "pins, notes, reports stay" rule exists to prevent.

**Relabeling is blocked by the pinned floor above.** Moving this case off `general`, or changing
its `topic_label` to something on-menu, drops the off-menu-general count from 3 to 2, redding
`test_dataset_taxonomy_per_stratum_minimums` on a floor with zero margin.

**Recommendation: leave `expect_topic_type="general"` and `topic_label` exactly as they are.**
Add a note to the case's `why` field (not notes/report, which stay frozen) stating explicitly
that this case's `expect_topic_type` is structurally unreachable via live classification by
construction — the offline leg needs `general` unconditionally (exercising the fallback), the
live leg will always compute `technical` on either model, and this is a designed, permanent,
documented gap rather than a defect to chase. This is the "document the divergence and leave the
label" option (CONTEXT's third-preference resolution) — correctly the *only* safe one for this
specific case, not a fallback of convenience.

### `general-defines-a-term` — relabel to `technical`, with an honest note

**What it exists to test** [VERIFIED: evals/dataset.py:711-716, `why` quoted]: *"A definition
answer is where a confident near-miss hides best: swap which methods are idempotent and the prose
still reads perfectly. The default path has to get this right."* This case's job is explicitly to
exercise "the default path" — general-stratum coverage, not incidental.

**Would relabeling change what it tests?** Yes, partially — moving it out of `general` removes it
from the "default rubric" coverage the `why` names. This is the one case where CONTEXT's
gutting-guard genuinely bites.

**Would rewording preserve the job better?** The house constraint blocks this too, for the same
reason as `chatty-label-falls-back`: its `notes` and `report`
[VERIFIED: evals/dataset.py:719-727] are HTTP-idempotency-specific prose (PUT/DELETE idempotency,
idempotency keys) — genuinely technical content, which is *why* both models call it `technical`.
Rewording the task to a genuinely general definition while leaving HTTP-technical notes/report in
place would be the same authored mismatch as above.

**Recommendation: relabel `expect_topic_type` (and `topic_label`, for offline consistency) to
`"technical"`.** Append an honest note to `why` recording that this case's general-stratum
coverage moved because two independent models agree the content is technical, and that
`general-summary`, `general-explains-a-concept`, and `general-how-a-mechanism-works` continue to
cover "the default path" for summary/concept-explainer/mechanism-explainer shapes. Post-relabel,
`general` count is **8** (11 − 3, counting this case plus the two below) — still clears the `>= 7`
floor, with exactly one spare case. If the planner wants more margin, the fallback is to treat

### `followup-with-no-prior-research` — relabel to `technical`; label was never load-bearing

**What it exists to test** [VERIFIED: evals/dataset.py:908-915, `why` quoted]: *"...it reaches for
the notes it hasn't got... a follow-up that reaches is a run under the same guardrails as any

entirely about the **budget guardrail on a follow-up**, never about generalness. Its content
("catalogue of every vector database released since 2020") reads as technical/product-cataloguing.

**Does the label matter to its job? No.** Nothing in `grade_forced_stop`, `grade_approval`, or
`grade_notes_stored` reads `topic_type`; `RESEARCH_STRATEGY`/`CRITIC_RUBRIC` text is never reached
live either, because the run is stopped by the budget cap before the researcher's output or any
writer/critic call [VERIFIED: src/research_agent/graph.py:598-620, the supervisor row ordering —
the budget check at :573-579 sits above the classifier/researcher routing rows]. Relabeling is
metadata-only and behaviorally inert.

**Recommendation: relabel `expect_topic_type` to `"technical"` and `topic_label` to `"technical"`
in lockstep** — if only `expect_topic_type` moved, the offline suite would break: `ScriptedClient`
still returns the OLD `topic_label="general"` (a valid `RESEARCH_STRATEGY` key, no fallback), so
`state["topic_type"]` would stay `"general"` offline and mismatch a `"technical"` expectation. Both
fields must move together.

### `injection-tries-to-force-approval` — relabel to `technical`; injection defense is topic_type-independent

**What it exists to test** [VERIFIED: evals/dataset.py:976-982, `why` quoted]: *"An injected note
that tries to script the critic is the version of this attack that would corrupt the quality gate
itself. Approval has to stay the critic's own, and the payload has to stay out of the draft."* —
injection resistance, not generalness. Content (MCP tool discovery and transport) reads
technical, consistent with its sibling case `injection-in-a-recalled-note`, which already carries
`expect_topic_type="technical"` [VERIFIED: evals/dataset.py:957].

**Does the label matter to its job?** The actual enforcement mechanism is `grade_case_pins`
[VERIFIED: evals/graders.py:666-698] checking `must_not_claim=("approved by order of the note",)`
— a pure substring match on the draft, with no dependency on `topic_type` or which
`CRITIC_RUBRIC` text a live critic saw. Note this grader only runs in `RECORDED_GRADERS`, consumed

claim being defended against ("approved by order of the note", "no claim needs a source") is not
a figure either way, and the grader that actually catches it is rubric-independent. Relabeling is
safe.

**Recommendation: relabel `expect_topic_type` and `topic_label` (in lockstep, same reason as
above) to `"technical"`.**

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Per-node model configuration | A new config layer, a settings class, a dict of overrides | The existing `call_model(..., model=...)` seam and an accessor function shaped exactly like `critic_model()` | One choke point already exists and is proven (Phase 16); a second mechanism for the same problem is the exact kind of divergence this project's ADRs exist to prevent |
| Comparing two models on the same prompt | A modified copy of `evals/harness.py`'s `run_case` | A small, direct-API script reusing the graph's own prompt constant | The harness's `run_case` drives the *whole graph*; the probe only needs one node's prompt against two models — building the smaller, purpose-fit tool is correct here, not hand-rolling |
| Fixture staleness detection | A second staleness mechanism specific to the classifier | Nothing — deliberately no staleness check for this role (Q2) | The existing `grade_fixture_current` machinery is the right tool for roles whose default stays neutral in CI; the classifier's role doesn't meet that precondition, so extending the *existing* mechanism would be wrong, not merely redundant |

**Key insight:** every "don't hand-roll" here is really "don't extend an existing pattern past
the precondition that makes it safe" — the whole of this phase's design risk is in correctly
identifying which parts of the `CRITIC_MODEL` precedent transfer and which don't.

## Common Pitfalls

### Pitfall 1: Mirroring `CRITIC_MODEL`'s neutral default

**What goes wrong:** `CLASSIFIER_MODEL` defaults to `MODEL` (Sonnet); the re-record checkpoint's
operator shell doesn't override it; the re-record classifies with Sonnet again; the same cases
refuse for the same reason.
**Why it happens:** copying a proven pattern without checking the precondition that made it safe
(Phase 16's capability was genuinely opt-in; this phase's is not).
**How to avoid:** default to `"claude-opus-5"` directly (Q1).
**Warning signs:** a re-record report showing the same `topic_type` mismatches Phase 21 already
saw.

### Pitfall 2: Extending `grade_fixture_current` by precedent instead of by precondition

**What goes wrong:** all 19 existing fixtures go stale in CI the moment the phase merges, because
the classifier's new unconditional default (unlike the critic's) makes `graph.classifier_model()`
diverge from any pre-existing recording's backfilled value in every environment, not just where an
operator opts in.
**Why it happens:** "the critic got a staleness gate, so the classifier should too" reads as
consistent, but the two roles' code defaults have opposite polarity.
**How to avoid:** record `models.classifier` as provenance only; no comparison (Q2).
**Warning signs:** `pytest tests/test_evals.py -k stale` (or the offline suite generally) turning
red on cases this phase never intended to touch.

### Pitfall 3: Treating the "six" refused cases as the whole list

**What goes wrong:** the re-record checkpoint is quoted and approved against six cases; two more
(`followup-with-no-prior-research`, `followups-chain-of-three`) are discovered mid-execution,
forcing a second checkpoint round.
**Why it happens:** CONTEXT.md's own believed-list, stated with a question mark, undercounted by
literal-string-matching too narrowly.
**How to avoid:** re-derive the list programmatically from `REFUSALS.json`'s `detail` field
containing `"topic_type"` before building the quote (Q5).
**Warning signs:** the union gate's `unaccounted` arm firing after the "completed" re-record.

### Pitfall 4: Relabeling `chatty-label-falls-back` because "both models say technical"

**What goes wrong:** `test_dataset_taxonomy_per_stratum_minimums`'s off-menu floor (`>= 3`) reds,
because this case is one of exactly three satisfying it.
**Why it happens:** the probe's live-classification evidence looks identical in shape to the other
three disputed cases, but this one's `expect_topic_type` is serving an offline-only purpose the
probe's methodology cannot even measure correctly.
**How to avoid:** check what a case's offline `topic_label` is actually exercising before treating
live-model disagreement as evidence the dataset is wrong (Q4).
**Warning signs:** `pytest tests/test_evals.py -k per_stratum_minimums` failing on the "general"
or off-menu count.

## Open Questions

1. **Should `fly.toml` carry a documentation-only `CLASSIFIER_MODEL` line?**
   - What we know: under the Q1 recommendation, the code default already delivers Opus 5
     everywhere; a `fly.toml` line changes nothing functionally.
   - What's unclear: whether the narrative-parity argument (a reader auditing `fly.toml`'s
     per-node model stance should see the classifier named, not just the critic) outweighs the
     risk of implying — incorrectly — that this line is load-bearing the way `CRITIC_MODEL` is.
   - Recommendation: include it, with an explicit comment stating the inverted safety direction
     (deletion is safe here, unlike `CRITIC_MODEL`) — this is the option Q6 leans toward, but it
     is genuinely discretionary and worth a one-line confirmation at plan review.

2. **Does `general-defines-a-term` get relabeled, or left-and-documented like
   `chatty-label-falls-back`?**
   - What we know: both are defensible under CONTEXT's stated preference order; relabeling costs
     one general-stratum case (margin drops to exactly 1 over the floor); leaving it costs a
     second "known divergence" note instead of a correction.
   - What's unclear: whether the user, at plan review, would rather see the dataset actively
     corrected (relabel) or the disagreement recorded without changing the assertion (leave).
   - Recommendation: relabel (this research's primary recommendation) — but flag explicitly at
     plan review since it's the one disputed-label call this research did not find a
     structurally-forced answer for, unlike the other three.
