21-CONTEXT's discretion areas were answered by 21-RESEARCH; four planning decisions remained
open and are settled here. The executor implements them as written.

**P-01 — The completeness gate is a repo-state pytest pin, NOT a change to the CLI's exit
rule.** 21-RESEARCH Open Question 2 left the choice open. The CLI's
"zero fixtures on disk is legal" property is load-bearing shipped design:
`test_zero_fixtures_is_still_green_prerecording` pins `main([]) == 0` on an empty
directory, `--case` selections replay subsets by design
(`test_replay_honours_the_case_selection`), and dozens of tests drive `main()` against
monkeypatched tmp directories that would all fail under an exit rule demanding the full
golden set. "This repo carries all 40" is an invariant of the COMMITTED TREE, not of any
one invocation — it belongs beside the other repo-state pins (Phase 20's
migration-bypass pin is the house precedent), and `pytest -q` runs on every push per
`ci.yml`, which satisfies the requirement's "on every push" literally
(21-RESEARCH Assumption A2 rates the alternative equivalent in enforcement).

**P-02 — The gate bites in BOTH directions, on stems.** `missing = golden − recorded` and
`orphans = recorded − golden`, computed from fixture file stems, because `write_fixture`
names files `{case_id}.json` (`fixtures.py:194`) — a stem that names no golden case is
either a dead fixture or a renamed dataset id, and both deserve a red naming the stem
(21-VALIDATION row 1: "both directions, or the gate only half-bites").

**P-03 — The judge scan compares `G.DEFAULT_JUDGE_MODEL`, not `G.JUDGE_MODEL` and not a
string literal.** `JUDGE_MODEL` is what THIS process resolved — a developer shell with
`EVAL_JUDGE_MODEL` exported would flip a repo-state pin about committed files, which is
absurd; and Phase 18-04's lesson stands: assert against the constant so re-pointing the
default re-points the gate. This scan deliberately does what `grade_fixture_current`
deliberately does not (`harness.py:383-389`): the CLI gate must not fail old verdicts when
the judge moves (they stay true statements about what the old judge said), but THIS phase's
entire premise is verdicts recorded once, under the settled judge — so the repo pin
compares the judge, and its firing on some future judge change is the re-record signal
working, not flakiness.

**P-04 — The real-directory pins land in 21-03, not here; here their logic is proven on
synthetic directories and the real tree's red is recorded as a measurement.** Committed
today, `test_every_golden_case_has_a_committed_fixture` would be red (39 missing) and every
commit must stay green. So wave 1 proves the helpers fire (unit tests constructing the
defect and asserting the named output), runs the same helpers against the real directory as
a COMMAND, and records the honest red — 39 missing, one stale judge — in the SUMMARY as
the pre-spend baseline. Wave 3 commits the one-line pins in the same tree state that makes
them green, then mutates the real directory to observe their reds (21-VALIDATION row 1's
mutation). Nothing is vacuous and nothing is committed red.
