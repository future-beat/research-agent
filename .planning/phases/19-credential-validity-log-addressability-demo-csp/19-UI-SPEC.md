# Phase 19 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This is a no-change contract.** Phase 19's UI surface work is a `Content-Security-Policy`
header on the demo page and JSON-only fields on `/health`. The page must come out of this
phase pixel-identical and behavior-identical. This document exists to pin what must NOT
change, to enumerate exactly what the CSP must permit (derived from the page as built), and
to forbid the improvements a well-meaning executor might otherwise slip in.

### Inline event handlers and style attributes

**Zero.** Verified by grep:

- No `onclick=`/`onsubmit=`/`onload=`/`onerror=`/`javascript:` anywhere. All wiring is
  `addEventListener` inside the script block (`form` submit at :528, session-row click at
  :456). **No handler-conversion work exists in this phase; the contract authorizes no
  edit to `index.html` at all** (see Change Budget below).
- No `style="…"` attributes and no `.style.` writes from JS (state changes are class-based:
  `classList.add`, `className`). So no `'unsafe-hashes'` is needed, and none is permitted.

### External resources

**Zero.** The only URLs in the markup are same-origin `<a href>` navigation links in the
footer (`/docs`, `/metrics`, `/health`, `/pricing`). Plain link navigation is not governed
by any fetch directive — these need nothing from the CSP. No images, no favicon `<link>`
(the browser's automatic `/favicon.ico` probe is browser-initiated, outside the page's CSP,
and 404s harmlessly today — no `img-src` is required).

### Network calls the script makes (all same-origin, all `connect-src`)

| Call site | Method + path | Purpose |
|-----------|---------------|---------|
| `run()` :335 | `POST /research/stream` or `POST /sessions/{id}/ask/stream` | The run itself. SSE parsed **by hand over `fetch` + `ReadableStream`** (`EventSource` cannot POST) — so SSE needs `connect-src`, not any special directive |

| `refreshSessions()` :471 | `GET /sessions` | The caller's own session list |
| `resume()` :490 | `GET /sessions/{id}` | Renders a stored conversation |

Five call sites, one origin. `connect-src 'self'` covers every one, including the SSE
streams (they are ordinary `fetch` responses).

## The CSP Contract

### Directive set

```
Content-Security-Policy:
  default-src 'none';
  script-src 'sha256-{hash of the single script block}';
  style-src 'sha256-{hash of the single style block}';
  connect-src 'self';
  base-uri 'none';
  form-action 'self';
  frame-ancestors 'none'
```

| Directive | Value | Why |
|-----------|-------|-----|
| `default-src` | `'none'` | The page loads nothing external by design; every capability below is opted in explicitly |
| `script-src` | one `sha256-…` source | The single inline `<script>` block, by hash. `'unsafe-inline'` is ruled out (CONTEXT: "a CSP with it is decorative") |
| `style-src` | one `sha256-…` source | The single inline `<style>` block, by hash (element hashes are CSP Level 2+; the dark-mode `@media` lives inside the same element, so dark mode costs nothing extra) |
| `connect-src` | `'self'` | The five same-origin fetch/SSE call sites above |
| `base-uri` | `'none'` | No `<base>` exists; forbid injection of one |
| `form-action` | `'self'` | The form's submit is `preventDefault`ed, but if JS ever failed the fallback GET-submit is same-origin; `'self'` permits it while forbidding exfiltration targets |
| `frame-ancestors` | `'none'` | Nothing embeds the demo; free clickjacking hardening, invisible to page behavior |

Not present, deliberately: `img-src` (no images), `font-src` (system stacks), `frame-src`,
`media-src`, `object-src` (covered by `default-src 'none'`), `'unsafe-hashes'` (no style
attributes or inline handlers exist to need it — and adding any would be the regression the
derivation test exists to catch).

`base-uri`/`form-action`/`frame-ancestors` are hardening that cannot affect rendering or
the demo flow. If the planner finds any of the three interferes with anything real, drop
that directive and note why — the requirement is the hash-based core, not the garnish.

### Reference hashes (informative, not normative)

As of the current page (last touched in commit `b2d6ccd`), SHA-256 over the exact UTF-8
bytes between the tags:

- script: `sha256-9r9Cu4iNyd4zpe8otNho5Q8WPI2YgqJmBM8l+2k7JnU=`
- style: `sha256-GjzXfxwdkdCrrRaX7wyDbcp+YGb15dhyT6JSLzaDWMg=`

**These literals are for orientation only. The policy is DERIVED from the page, never
hand-maintained** — see the invariant below. If these bytes drift from the file, the file
wins and a test says so.

### The derivation invariant (the load-bearing clause)

- A test extracts the inline blocks from `static/index.html` (the real file, not a
  fixture), hashes them, and asserts the served/derived policy contains exactly those
  hashes and no `'unsafe-inline'`. **Editing the page without the policy following it
  fails a test** rather than silently breaking the live demo.
- Where hashes are computed — build-time constant plus derivation test, or startup
  derivation — is planner discretion per 19-CONTEXT, provided the drift-fails-a-test
  property holds either way.
- The test must also assert the counts: exactly one script block, exactly one style block,
  zero inline event-handler attributes, zero `style=` attributes. A second inline block or
  a first `onclick=` changes the policy's shape, not just its hashes.

### Where the header attaches

- **MUST:** the `text/html` branch of `index()` — the `FileResponse` carrying
  `DEMO_PAGE`. That response is the requirement's entire scope.
- **MAY:** the JSON branch of `GET /` too, or a broader mechanism (middleware), at the
  planner's discretion — a CSP on a JSON response is inert. What is NOT authorized is any
  mechanism that alters other responses' existing headers (the SSE responses'
  `Cache-Control: no-cache` / `X-Accel-Buffering: no` must survive untouched).

### Cookie non-interaction (stated so nobody re-litigates it)

The identity cookie is minted by `IdentityMiddleware` on the first response, is `HttpOnly`,
and is never touched by page JS. **CSP has no cookie directives; no directive above can
affect cookie setting, sending, or the middleware.** The acceptance check still confirms
it empirically: first visit with the header present still mints the cookie, and the first
run's session lands in "Your recent research".

## What Must NOT Change (the pin list)

This page is the portfolio's front door. The following are invariants; violating any is a
phase failure even if every test passes:

1. **Visual identity** — the palette (`--bg #fbfaf8 / --fg #1c1a17 / --accent #7c4a2d` and
   the full custom-property set, light and dark), the serif/mono type pairing, the 46rem
   single-column layout, cards, badges, stage rows. Byte-identical `<style>` block.
2. **The demo flow** — ask → stage rows stream in (classify, search, draft, critic
   rejects/approves, redraft) → result card with badges → follow-up via placeholder swap →
   session list and resume. Byte-identical `<script>` block.
3. **The page file itself** — see Change Budget. The CSP is derived FROM the page; the
   page is not adapted TO the CSP. No inventory item requires it to be.
4. **Cookie behavior** — HttpOnly identity cookie, minted silently by middleware, invisible
   footprint limited to the existing footer sentence.
5. **The surfaces the page reads** — `/demo`, `/sessions`, `/sessions/{id}`, and both
   stream endpoints keep their shapes (this phase touches none of them). The footer links
   to `/metrics` and `/pricing` stay links.
6. **SSE headers** — `Cache-Control: no-cache` and `X-Accel-Buffering: no` on streaming
   responses stay exactly as they are.

### Change budget for `static/index.html`: **zero edits.**

No inline handlers exist to convert, no style attributes exist to hoist, no external
resources exist to inline. If planning or execution discovers that satisfying the CSP
somehow forces an edit to the page, **that surfaces as a checkpoint to the user** (per
19-CONTEXT: "a checkpoint, not a silent rewrite") — it is not authorized here.

## Acceptance Checks (how a human verifies "nothing changed")

1. **Header present:** `curl -sI -H "Accept: text/html" https://{app}/ | grep -i content-security-policy` — header exists, contains both `sha256-` sources, contains no `unsafe-inline`.
2. **Page identical:** open the live page in a browser (light and dark). Layout, colors, type all as before; DevTools console shows zero CSP violations on load.
3. **Full demo flow:** ask a question → stage rows stream in (classifier, researcher, writer, critic — including a rejection if one occurs) → result card with badges → placeholder flips to the follow-up copy → ask a follow-up into the same session. Zero console violations throughout.
4. **Periphery:** limits line populates from `/demo`; "Your recent research" appears after the run and a session resumes; footer links navigate.
5. **Cookie:** first visit in a fresh private window still mints the identity cookie (DevTools → Application → Cookies), and the run's session appears under "Your recent research" — CSP did not touch identity.
6. **Drift guard:** the derivation test passes in the keyless suite; deliberately perturbing one byte of the script block makes it fail.
7. **/health:** new credential-validity fields appear in the JSON beside the presence booleans; the demo page is visually and behaviorally indifferent to them.
