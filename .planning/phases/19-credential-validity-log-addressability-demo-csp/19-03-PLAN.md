<decisions_this_plan_locks>
**P-07 — The service emits `run_finished`; the graph's terminal line becomes
`graph_finished`.** 19-RESEARCH left the event name open (Open Question 1) and warned that a
second call site sharing the name double-counts every HTTP run (Pitfall 1). Its own suggestion
was a new name for the service line. This plan inverts that, for three reasons:

1. REQ-run-finished-session-id and ROADMAP success criterion 4 both say `run_finished` lines
   carry `session_id`. Under the researcher's assignment, the line named `run_finished` would
   still not carry it, and the requirement would be met only by reinterpretation. Under this
   assignment it is met literally.
2. The rename is free. `run_finished` appears exactly ONCE in the entire repository outside
   planning documents — `graph.py:638` — with no test, no doc, no eval and no dashboard
   reading it. There is nothing to break. (Measured by repo-wide grep during planning; Task 1
   re-measures rather than trusting this sentence.)
3. The two names then say two different true things. The graph reached its terminal state;
   the run was persisted and is addressable. Under the researcher's assignment, the more
   important of those two facts would carry the less important name.

`AgentState` is NOT touched. 19-RESEARCH proved empirically that LangGraph 1.2.9 silently
drops undeclared state keys, so the tempting workaround does not merely fail — it fails
silently, which is the Phase 17 failure mode again one level down. And for a brand-new session
`session_id` does not exist yet while the graph runs: `store.create()` mints it inside
`on_complete`, AFTER `graph.app.invoke` returns. The graph structurally cannot carry it.

**P-08 — The emission sits immediately after `metrics.record(...)`, inside the `try`.** Then
the line means both writes landed, and the existing `run_failed` in the except arm is its exact
complement: every HTTP-initiated run emits precisely one of the two.
</decisions_this_plan_locks>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| service process → log sink | Structured records leave the process for `fly logs` and any aggregator; whatever a record carries is readable by anyone with log access. |
| log stream → operator counting | Event names are the schema an operator counts against; a name that means two things silently corrupts their arithmetic. |
| repository → published docs | README and OPERATIONS are what a stranger reads to decide whether the claims hold. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19-11 | Information Disclosure | the completion record's fields | low | accept | `session_id` is an opaque UUID and `run_id` already ships alongside it; no PII, no question text and no credential enters the record. Accepted with the same reasoning `run_id` was. |
| T-19-12 | Repudiation | completion counting | medium | mitigate | P-07 gives each call site an honest, distinct name and Task 2 pins exactly-one-per-run plus zero-on-failure. Two lines sharing a name is the double-count this register exists to prevent. |
| T-19-13 | Tampering | log-injection via a question echoed into a record | low | accept | The record carries no caller-controlled free text — every field is an id, an enum, a bool or a number — and the JSON formatter escapes values regardless. Nothing new to mitigate. |
