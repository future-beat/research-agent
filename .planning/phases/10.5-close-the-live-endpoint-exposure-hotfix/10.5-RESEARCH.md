# Phase 10.5: Close the live endpoint exposure (hotfix) - Research

**Researched:** 2026-08-04
**Domain:** FastAPI authorisation composition, dependency scoping, deploy-time secret cutover
**Confidence:** HIGH (everything load-bearing was verified by executing code in this tree)

## Summary

The defect is exactly as described and the mechanics are now fully established. `guard`
(`service.py:134`) is a thin wrapper over `limits.enforce` (`limits.py:208`), which runs
`check_token` → `check_rate_limit` → `check_daily_cap` as one indivisible unit. Four session
routes carry no dependency at all beyond `get_sessions`, verified by introspecting the live
route table in this tree. `DEMO_TOKEN` is inert on them because `check_token` only ever runs
inside `enforce`.

**The single most important finding inverts the brief's hypothesis.** The demo page does *not*
call any of the four leaking endpoints — it calls `POST /research/stream`, `POST
/sessions/{id}/ask/stream`, and `GET /demo`, and nothing else (`static/index.html:262,263,346`;
the whole file contains exactly two `fetch` calls). Guarding the four reads therefore cannot
break the demo. What *would* break the demo is the obvious remediation: setting `DEMO_TOKEN` as
a Fly secret to close the reads also closes `POST /research/stream`, which is already inside
`guard`, and the browser page sends no `x-demo-token` header. **Setting `DEMO_TOKEN` in
production kills the demo and is not an available fix.** The phase needs a credential that is
separable from the write-path token.

Second finding, also structural: `guard` is the wrong tool for reads, for the reason the
codebase already argues in two docstrings. Applying `guard` to `GET /sessions` would make reads
consume the visitor's 10-runs-per-hour research quota, and would make reads return 429 once the
$5 daily cap is hit — while the cap's own error message says "Read-only endpoints still work"
(`limits.py:203`). The correct decomposition is a token-only dependency for the reads, plus
`check_rate_limit` added on `DELETE` alone.

**Primary recommendation:** Add `require_sessions_token` to `limits.py` — reads `SESSIONS_TOKEN`,
falls back to `DEMO_TOKEN`, **fails closed (403) when neither is set** — and mount the four
routes on an `APIRouter(prefix="/sessions", dependencies=[Depends(require_sessions_token)])`,
with `dependencies=[Depends(check_rate_limit)]` added on the `DELETE` decorator only. Leave the
two `POST /sessions/{id}/ask*` routes on `app` with their existing `Depends(guard)`. Set
`SESSIONS_TOKEN` (not `DEMO_TOKEN`) as a Fly secret. Fix `service.py:263` with
`_redact(str(exc))[:160]`.

### Verified guard composition

`guard` (`service.py:134`) → `limits.enforce(request, metrics)` (`limits.py:208`) → three checks,
in this order and with these documented reasons (`limits.py:209-214`):

| Check | Reads | Effect on a *read* endpoint if `guard` were applied |
|-------|-------|----------------------------------------------------|
| `check_token` (`limits.py:172`) | `DEMO_TOKEN`; **no-op when unset** | Correct and wanted. |
| `check_rate_limit` (`limits.py:183`) | per-IP sliding window, 10/hr default | **Wrong for reads.** A visitor listing sessions would consume the quota that exists to bound *spend*. Ten `GET`s and the visitor can no longer run research. |
| `check_daily_cap` (`limits.py:194`) | `metrics.spend_since()` | **Wrong for reads.** Once the demo hits $5, every read 429s — while the 429 body literally says "Read-only endpoints still work." It also costs a DB round trip per read, and `/health`-style diagnosability disappears exactly when it is needed. |

**Conclusion: `guard` is the wrong tool for the three GETs.** It is *nearly* right for `DELETE`
(token + rate limit are both wanted) but `check_daily_cap` is still wrong there — a delete spends
no money, and refusing a delete because the *research* budget is exhausted is nonsense. Compose
explicitly instead of reaching for `guard`.

### Pattern 1: A token dependency that fails closed, separable from `DEMO_TOKEN`

**What:** A new `limits.require_sessions_token` that mirrors `check_token`'s comparison but (a)
reads `SESSIONS_TOKEN` with a `DEMO_TOKEN` fallback, and (b) refuses when *no* token is
configured, instead of passing.

**Why not just reuse `check_token`:** `check_token` returns early when the token is unset
(`limits.py:174-175`). That is correct for the write path — it is what keeps the demo open by
default. Reusing it on the sessions router means the leak stays open on any deployment that
forgets the secret, which is precisely the failure that produced this phase. SC-1 says
"not reachable without credentials **on the deployed service**"; a dependency that no-ops on a
missing env var cannot guarantee that.

**Why a new variable rather than `DEMO_TOKEN`:** `DEMO_TOKEN` gates `POST /research/stream`,
which the browser page calls with no auth header (`static/index.html:272-276`). Setting
`DEMO_TOKEN` in production returns 401 to every anonymous visitor and destroys the portfolio
demo. The fallback keeps SC-2 literally true (setting `DEMO_TOKEN` *does* protect them) while
giving production a way to close the reads without closing the writes.

**Status codes:** 403 when nothing is configured ("nobody can pass"), 401 when a token is
configured and the caller's is absent or wrong. Both satisfy SC-1/SC-6's "401/403". Do not use
503 — SC-6 asks for 401/403 specifically.

**Example (follows `limits.py` conventions — per-call env read, named for what it returns,
`hmac.compare_digest`, reason-bearing comment):**

```python
# Source: pattern derived from limits.py:172-180 (check_token) in this tree
def sessions_token() -> str:
    """The credential for reading and deleting sessions.

    Separate from DEMO_TOKEN because they close different doors. DEMO_TOKEN
    gates the endpoints that spend money, and the demo page cannot send a
    header -- setting it in production would 401 every anonymous visitor and
    turn the demo into a dead link. SESSIONS_TOKEN closes the session tree
    without touching the demo. DEMO_TOKEN is still honoured as a fallback, so
    "setting DEMO_TOKEN protects the session endpoints" is true rather than,
    as it was until this change, silently false.
    """
    return os.environ.get("SESSIONS_TOKEN", "").strip() or demo_token()


def require_sessions_token(request: Request) -> None:
    """Unlike check_token, this refuses when no token is configured.

    check_token no-ops on an unset DEMO_TOKEN, which is what keeps the demo
    open by default. Carrying that behaviour here is what left every stored
    report world-readable on the deployed service: the control was present in
    the code and inert in production. These endpoints fail closed.
    """
    token = sessions_token()
    if not token:
        raise HTTPException(403, "Session endpoints are closed: no SESSIONS_TOKEN is set.")
    supplied = request.headers.get("x-demo-token", "")
    if not supplied or not hmac.compare_digest(supplied, token):
        raise HTTPException(401, "A valid X-Demo-Token header is required.")
```

Reuse the `x-demo-token` header name rather than inventing `x-sessions-token`: one header, one
client-side story, and SC-2's "setting `DEMO_TOKEN` protects them" then works with no extra
knowledge on the caller's part.

### Pattern 2: Router-level dependency for the group, decorator-level for the extra

**What:** Move the four routes onto an `APIRouter` whose `dependencies=` carries the token check;
add `check_rate_limit` on the `DELETE` decorator only.

**Why router-level:** FastAPI documents that router `dependencies` "will be added to all the
_path operations_ in the router" and that "the router dependencies are executed first, then the
`dependencies` in the decorator, and then the normal parameter dependencies"
[CITED: https://fastapi.tiangolo.com/tutorial/bigger-applications/]. That ordering is exactly
what is wanted: reject the unauthorised caller *before* spending a rate-limit slot — the same
cheapest-first, don't-let-an-unauthorised-caller-consume-quota reasoning already written at
`limits.py:209-213`.

A future `@sessions.get("/{id}/notes")` inherits the guard by construction. A per-route
`dependencies=[...]` list would not, and per-route is how this bug happened: the four money
endpoints each got the decorator and the four session endpoints each did not.

**The trap that makes the naive router split wrong:** `POST /sessions/{id}/ask` and
`/sessions/{id}/ask/stream` also live under `/sessions`. If they are moved onto the same router,
they inherit `require_sessions_token`, and **follow-ups — the demo's second turn — break for
anonymous visitors.** Group by *dependency*, not by path prefix. Two routers may both contribute
paths under `/sessions`; FastAPI matches on the full path, and `/sessions/{id}/ask` and
`/sessions/{id}` are distinct patterns. Verified working in this tree's FastAPI 0.141.1
(see § Code Examples 1).

**Example:**

```python
# Source: verified against fastapi 0.141.1 in this tree
sessions = APIRouter(
    prefix="/sessions",
    tags=["sessions"],
    dependencies=[Depends(limits.require_sessions_token)],
)

@sessions.get("")
def list_sessions(store: SessionStore = Depends(get_sessions)) -> dict: ...

@sessions.get("/{session_id}", response_model=SessionDetail)
def get_session(session_id: str, store: SessionStore = Depends(get_sessions)): ...

@sessions.get("/{session_id}/trace")
def get_trace(session_id: str, store: SessionStore = Depends(get_sessions)) -> dict: ...

@sessions.delete(
    "/{session_id}",
    status_code=204,
    # Router deps run first, so an unauthorised caller is refused before it
    # can consume a rate-limit slot -- same ordering rationale as
    # limits.enforce. The bucket is shared with research runs by design: one
    # limiter, one key space, no second global to reset.
    dependencies=[Depends(limits.check_rate_limit)],
)
def delete_session(session_id: str, store: SessionStore = Depends(get_sessions)) -> None: ...

app.include_router(sessions)   # after the @app.post("/sessions/{id}/ask*") routes
```

`@sessions.get("")` with `prefix="/sessions"` produces the path `/sessions` exactly — no trailing
slash, no double prefix [VERIFIED: route table printed in this tree].

If the secret is somehow missing at step 2, the fail-closed dependency returns 403 to everyone
including the owner — inconvenient, never leaky. That is the correct direction to fail.

**Cost warning:** step 4's browser run is a real research run against the real API, roughly $0.15
at current rates, and it counts against `DEMO_DAILY_USD_CAP`. Budget one. **Rate-limit warning:**
the `curl`s in step 3 that hit rate-limited paths (`DELETE`) consume the verifying machine's
10/hour bucket.

### Pattern 4: A structural test that a future route cannot be added unguarded (SC-5)

This is the criterion with a real trap in it, and it is version-specific.

**FastAPI 0.141 no longer flattens included routers into `app.routes`.** `include_router` leaves
a single `fastapi.routing._IncludedRouter` object that resolves routes at match time. A test that
does the obvious thing —

```python
for r in app.routes:
    if isinstance(r, APIRoute) and r.path.startswith("/sessions"): ...
```

— finds **zero** session routes once they live on a router, iterates an empty list, and **passes
vacuously**. It would then keep passing forever while the endpoints were wide open. This is the
same class of silent-skip failure the repo already defends against at
`tests/test_store_contract.py:441`, and the fix follows the same convention: assert the test
actually examined something.

[VERIFIED: executed in this tree — `app.routes` after `include_router` contains
`fastapi.routing._IncludedRouter` objects, not `APIRoute`; routes declared with `@app.get`
directly are still `APIRoute`.]

Two facts that make a correct test easy, both verified here:

- Router-level dependencies **are** visible on the router's own `APIRoute` objects:
  `route.dependant.dependencies[i].call.__name__` includes `require_sessions_token`.
- `route.path` on a router built with `prefix="/sessions"` already carries the prefix; only a
  prefix passed to `include_router(..., prefix=...)` needs composing.

Working walker, verified against both shapes:

```python
# Source: verified against fastapi 0.141.1 / starlette 1.3.1 in this tree
from fastapi.routing import APIRoute

try:
    from fastapi.routing import _IncludedRouter
except ImportError:            # FastAPI < 0.141 flattened included routers
    _IncludedRouter = ()

def api_routes(app):
    """Every APIRoute the app serves, including ones behind include_router.

    FastAPI 0.141 stopped flattening included routers into app.routes: an
    include leaves one _IncludedRouter that resolves at match time. Filtering
    app.routes for APIRoute alone therefore finds nothing on a router and
    passes over an empty list -- which is how a guard test would go green on
    a wide-open service.
    """
    found = []
    def walk(routes, prefix=""):
        for r in routes:
            if isinstance(r, APIRoute):
                found.append((prefix + r.path, r))
            elif _IncludedRouter and isinstance(r, _IncludedRouter):
                walk(r.original_router.routes, prefix + r.include_context.prefix)
    walk(app.routes)
    return found

def dependency_names(route) -> set[str]:
    return {getattr(d.call, "__name__", "") for d in route.dependant.dependencies}
```

Where this helper lives: per `TESTING.md`, **no `conftest.py`** — put it in
`tests/test_service.py` (the module that owns the API surface) and let any other module import it
by name, the way `FakeClient` is imported from `test_graph_smoke`.

The assertion (SC-5's "fail if a future endpoint is added to the sessions group without a guard"):

```python
AUTH_DEPENDENCIES = {"guard", "require_sessions_token"}

def test_no_session_route_is_reachable_without_a_guard():
    """The bug this phase exists to fix was four routes that each individually
    forgot a decorator. Assert the property over the route table instead of
    trusting four decorators to stay correct."""
    routes = [(p, r) for p, r in api_routes(service.app) if p.startswith("/sessions")]

    # Guard against the vacuous pass: if the walker stops finding routes --
    # because a future FastAPI changes how include_router stores them -- this
    # test must fail rather than silently examine nothing.
    assert len(routes) >= 6, f"route walker found only {len(routes)} /sessions routes"

    unguarded = [
        (sorted(r.methods), p) for p, r in routes
        if not (dependency_names(r) & AUTH_DEPENDENCIES)
    ]
    assert unguarded == []
```

Plus a companion asserting `check_rate_limit` specifically on the `DELETE` (SC-3), which no
behavioural test can prove cheaply — `DEMO_RATE_LIMIT_PER_HOUR` is 0 in the fixture, and driving
11 real deletes to observe a 429 is slower and more brittle than asserting the wiring. Assert
both: the wiring structurally, and one behavioural 429 with the limit monkeypatched to 1.

### Anti-Patterns to Avoid

- **Applying `guard` to the three GETs.** Drags in the daily spend cap and the research quota;
  contradicts `limits.py:203`'s own promise and `service.py:136-140`'s diagnosability rationale.
- **Setting `DEMO_TOKEN` in production.** Closes the demo. It is the fix that looks obvious and
  is wrong.
- **Putting the sessions credential in `fly.toml` `[env]`.** That file is committed. Secrets go
  through `fly secrets set`. The file already carries a comment saying so (`fly.toml`, near
  `DEMO_DAILY_USD_CAP`).
- **Moving `POST /sessions/{id}/ask*` onto the guarded router** because they share the prefix.
  Breaks follow-ups for anonymous visitors — the demo's second turn.
- **Modelling identity, ownership, or expiry.** Phase 12. The scope fence is explicit in ROADMAP
  and REQUIREMENTS.
- **A `conftest.py` for the new test helper.** Against a documented, deliberate convention.
- **Iterating `app.routes` for `APIRoute` without recursing into `_IncludedRouter`.** Passes
  vacuously; see Pattern 4.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Constant-time token compare | `supplied == token` | `hmac.compare_digest` | Already the pattern at `limits.py:179` with a comment explaining it |
| Redacting DSN passwords from error text | A new regex at the SSE site | `service._redact` (`service.py:337`) + `[:160]` truncation, as `_probe` does (`service.py:361`) | The helper exists, is correct, and is tested (`tests/test_service.py:681-689`). SC-4 says explicitly the call site "just is not wired to it" |
| Applying a dependency to a route group | A path-prefix middleware or a decorator on each route | `APIRouter(dependencies=[...])` | Per-route is exactly how four routes each forgot the guard |
| Identifying the caller behind Fly's proxy | Reading `X-Forwarded-For` | `limits.client_ip` (`limits.py:71`) | Prefers unforgeable `Fly-Client-IP`; the trust model is documented and tested (`tests/test_limits.py:47,55`) |
| Per-IP sliding window | A new counter | `limits.check_rate_limit` / `RateLimiter` | Already has sweeping, locking, and `Retry-After` |

**Key insight:** every primitive this hotfix needs already exists in `limits.py` and was already
tested. The defect is entirely one of *composition and application*, not of missing capability.
The plan should read as wiring, not as building.

## Common Pitfalls

### Pitfall 1: "Just set `DEMO_TOKEN`" takes the demo offline
**What goes wrong:** `DEMO_TOKEN` is checked by `guard`, which already fronts `POST
/research/stream` and `POST /sessions/{id}/ask/stream`. The demo page issues those with
`headers: { "content-type": "application/json" }` and nothing else
(`static/index.html:272-276`). Every anonymous visitor gets 401, and the page's error handler
dutifully renders "Request refused (HTTP 401)" (`index.html:283-291`).
**Why it happens:** The variable's name and the fact that it is the only existing token make it
look like the intended lever.
**How to avoid:** Separate variable (`SESSIONS_TOKEN`) with `DEMO_TOKEN` as fallback. Never set
`DEMO_TOKEN` on the production app.
**Warning signs:** `GET /demo` returns `"token_required": true` — `limits.status()` surfaces this
at `limits.py:225`, and the page prints "a demo token is required" (`index.html:352`).

### Pitfall 2: Fourteen existing test call sites hit these routes with no token
**What goes wrong:** `make_client` deliberately does `monkeypatch.delenv("DEMO_TOKEN")`
(`tests/test_service.py:40`). With a fail-closed dependency, every existing call to the four
routes starts returning 403.
**Exact inventory** (all in `tests/test_service.py`) — verified by grep:

| Line | Call | Currently asserts |
|------|------|-------------------|
| 144 | `GET /sessions/{id}` | detail fields |
| 208 | `GET /sessions/{id}` | turns after two follow-ups |
| 243 | `GET /sessions` | newest-first ordering |
| 252 | `GET /sessions/{id}/trace` | node sequence |
| 262, 263, 264 | `DELETE`, `GET`, `DELETE` again | 204 / 404 / 404 |
| 267 | parametrised `["/sessions/nope", "/sessions/nope/trace"]` | 404 |
| 312 | `GET /sessions/{id}` | detail after stream |
| 333 | `GET /sessions/{id}` | turns == 2 |
| 372 | `GET /sessions` | empty after a failed stream |
| 423 | `GET /sessions` | empty |
| 499 | `GET /sessions` | empty |
| 814 | `GET /sessions` | empty — **and this one sets `DEMO_TOKEN="s3cret"` at line 810**, so it breaks under *any* design, including the non-fail-closed one |

**How to avoid:** Set `SESSIONS_TOKEN` in the `make_client` fixture alongside the other guardrail
env vars and have the fixture's `TestClient` send `x-demo-token` by default —
`TestClient(app, headers={"x-demo-token": TOKEN})` sets a default header on every request, so no
existing call site needs editing except the negative tests. That is the smallest diff and keeps
the fixture as the single place that knows about credentials, matching how it already owns
`DEMO_RATE_LIMIT_PER_HOUR` / `DEMO_DAILY_USD_CAP` / `SESSION_BACKEND`.
Line 814 needs an explicit fix regardless — that test is about spend, not auth, and should assert
emptiness through a client that carries the sessions token.
**Warning signs:** a large diff full of `headers={...}` sprinkled across unrelated tests.

### Pitfall 3: Guarding changes the status code for unknown sessions
**What goes wrong:** `test_unknown_sessions_are_404` (`tests/test_service.py:267`) asserts 404 for
`/sessions/nope`. With a router-level dependency, an unauthenticated caller now gets 401 *before*
`_require` runs.
**Why it happens:** Auth runs before the handler — which is correct: 404-before-401 leaks whether
a session ID exists.
**How to avoid:** Keep the test asserting 404 *with* a valid token, and add a sibling asserting
401 without one. Both facts are worth pinning.

### Pitfall 4: The rate-limit bucket is shared with research runs
**What goes wrong:** `check_rate_limit` keys on `client_ip(request)` against one process-global
`RateLimiter` sized by `DEMO_RATE_LIMIT_PER_HOUR` (default 10). An operator deleting 11 sessions
gets 429 — and has also consumed the research quota for that IP.
**Why it happens:** One limiter, one key space (`limits.py:152-161`).
**How to avoid:** Accept it for the hotfix and *document it in the docstring*. A second limiter
means a second module global and a second entry in `reset_limiter()`. Note also the limiter is
**per process** — with `min_machines_running = 1` today this is exact, but Phase 11 raises machine
count and each machine will allow the full quota (`limits.py:94-98` already says so).
**Warning signs:** an unexplained 429 on a `DELETE` right after a demo run from the same IP.

### Pitfall 5: `_redact` alone is not the whole fix at `service.py:263`
**What goes wrong:** `_redact(str(exc))` without truncation still emits an arbitrarily long
exception body over the wire, and the browser renders it (`index.html:327`).
**Why it happens:** The SSE site was never wired to the helper at all, so the truncation `_probe`
applies (`service.py:361`, `[:160]`) is easy to forget too.
**How to avoid:** Mirror `_probe` exactly: `_redact(str(exc))[:160]`. Consider also taking the
first line, as `_probe` does at `service.py:357` — a psycopg error is multi-line and the second
line is where the DSN often sits.
**Warning signs:** a test that only asserts the password is gone, without asserting length.

### Pitfall 6: Docs that will become false the moment this ships
Four places currently assert the open-reads design as intentional. All must change in the same
commit or the repo contradicts itself:

| File:line | Current text | Why it breaks |
|-----------|--------------|---------------|
| `limits.py:24-26` | "Read-only endpoints (`/health`, `/metrics`, **`/sessions`**, the demo page) are never gated" | Directly false after the change |
| `limits.py:8-11` | "`DEMO_TOKEN` … write endpoints need an `X-Demo-Token` header" | Now also reads/deletes, via `SESSIONS_TOKEN` |
| `service.py:135-140` | `guard`'s docstring: "Read-only endpoints stay open on purpose" | Needs the distinction between *ops* reads and *session* reads that CONCERNS.md draws |
| `README.md:81`, `README.md:203` | API table lists the session reads with no auth note; "Anyone who can reach the service can read any session" | The second sentence stops being true |
| `docs/OPERATIONS.md:137` | `DEMO_TOKEN` env table row | Needs a `SESSIONS_TOKEN` row |
| `.env.example` (last block) | Documents `DEMO_TOKEN` only | Needs `SESSIONS_TOKEN` |
| `service.py:302-330` (`_index_json`) | Advertises `sessions`/`session`/`trace` with no hint they need a token | Cosmetic but cheap |

## Open Questions

1. **SC-2 and the demo's survival are in direct tension. Which reading of SC-2 wins?**
   - *What we know:* SC-2 says "Setting `DEMO_TOKEN` actually protects them." Setting `DEMO_TOKEN`
     on the production app also 401s the demo page's own `POST /research/stream`, because the page
     sends no header. Verified from `static/index.html:272-276` and `service.py:461`.
   - *What's unclear:* whether SC-2 means "the mechanism must be `DEMO_TOKEN` specifically" or
     "the token control must no longer be inert on these paths."
   - *Options:* (a) `SESSIONS_TOKEN` with `DEMO_TOKEN` fallback — SC-2 literally true, demo lives
     [recommended]; (b) one token and teach the page to send it — impossible, a public page's JS
     is not a secret store; (c) drop the four endpoints in production entirely (404 unless a token
     is configured) — satisfies SC-1 absolutely, needs no secret, cannot regress, and the demo
     never used them; arguably the most honest answer for a portfolio demo, but it changes the
     public API surface and edges toward Phase 12's "should `GET /sessions` exist at all".
   - *Recommendation:* (a). Raise (c) in discuss-phase as the simpler alternative and let the user
     choose. This is the phase's one genuine decision.

2. **Fail closed, or inherit `check_token`'s open-when-unset semantics?**
   - *What we know:* fail-closed costs ~14 test call-site fixes (one fixture change, per Code
     Example 3) and breaks `curl localhost:8000/sessions` for a developer who has set nothing.
     Open-when-unset costs one test fix and leaves SC-1 dependent on an operator action.
   - *Recommendation:* fail closed. The bug being fixed *is* "a control that was present in the
     code and inert in production."

3. **Does `GET /metrics` belong in this phase?**
   - *What we know:* CONCERNS.md flags `/metrics` as unauthenticated and holding an unbounded
     query that an anonymous caller can use to occupy the single lock-guarded DB connection
     (CONCERNS.md ~line 310-330).
   - *Recommendation:* **no.** It is not in REQ-live-endpoint-exposure and not in the six criteria.
     `/metrics` leaks aggregates, not content. Leave it; note it for Phase 11/12.

4. **Should the `/demo` status payload advertise `sessions_token_required`?**
   - *What we know:* `limits.status()` (`limits.py:220`) surfaces `token_required` from
     `demo_token()`. A separate sessions token would not appear.
   - *Recommendation:* leave it. The demo page is the only consumer and it has no use for the
     fact. Adding a field means touching the page and its tests for no user-visible gain.

### Known Threat Patterns for FastAPI + Fly + shared-token demo

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Unauthenticated read of other users' data (BOLA/BFLA, the confirmed defect) | Information Disclosure | Deny-by-default router dependency; structural test that no route escapes it |
| Unauthenticated destructive delete | Denial of Service / Tampering | Same dependency + `check_rate_limit` on the `DELETE` |

| Secret committed to the repo | Information Disclosure | `fly secrets set`, `.env` gitignored and excluded from the Docker build context |
| Auth check ordered after existence check (404 vs 401 oracle) | Information Disclosure | Router dependencies run before the handler — automatic here; keep it that way |
| CORS widening the blast radius | Information Disclosure | No CORS middleware is registered; same-origin only. **Do not add one in this phase.** |
