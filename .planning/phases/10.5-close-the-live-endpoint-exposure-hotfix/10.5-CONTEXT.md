# Phase 10.5: Close the live endpoint exposure (hotfix) - Context

**Gathered:** 2026-08-04
**Status:** Ready for planning
**Source:** Decisions taken directly after research (no discuss-phase run — the phase's one

<domain>
## Phase Boundary

This phase stops the deployed service handing session contents to anonymous callers and
stops it accepting anonymous deletes. It reuses and decomposes the auth machinery that
already exists in the codebase.

It does **not** introduce an identity model. Per-caller ownership, session expiry and note
lifecycle are Phase 12 and are out of bounds here.

</domain>

<decisions>
## Implementation Decisions

### Protection mechanism

- **A new `SESSIONS_TOKEN` guards the four session endpoints**, with `DEMO_TOKEN` accepted
  as a fallback value. `DEMO_TOKEN` keeps its current meaning and stays unset in production.
- **Rationale (this is the load-bearing one):** `guard` already checks `DEMO_TOKEN` and
  fronts `POST /research/stream`. The demo page sends no `x-demo-token` header, so setting
  `DEMO_TOKEN` in production would 401 every anonymous visitor and kill the public demo —
  the project's entire portfolio purpose. Verified: `static/index.html` has exactly two
  `fetch` calls (line 272 and line 346) and never touches the four leaking endpoints, so
  guarding those endpoints is safe; it is `DEMO_TOKEN` specifically that is unsafe to set.
- The four endpoints remain reachable with the token, so live sessions can still be
  inspected over HTTP for debugging.

### Failure default

- **Fail closed.** When `SESSIONS_TOKEN` is unset, the four endpoints refuse everyone (403).
- **Rationale:** the defect being fixed is precisely a control that existed in code and was
  inert in production. A design where forgetting to set the secret silently reopens the hole
  repeats the exact mistake. This deliberately diverges from `check_token`'s existing
  open-when-unset convention, and costs ~14 test call-site updates.

### Dependency composition

- **Do not apply `guard` to the read endpoints.** `guard` → `limits.enforce` is
  `check_token` + `check_rate_limit` + `check_daily_cap`, indivisibly. Applying it to reads
  would make listing sessions consume the caller's 10-runs/hour research quota, and would
  429 all reads once the $5 daily cap is hit — directly contradicting the cap's own message
  "Read-only endpoints still work" (`limits.py:203`).
- Correct decomposition: a **token-only, fail-closed dependency** on the group, plus
  `check_rate_limit` on `DELETE` only (the destructive path).

### Grouping

- Group the four endpoints **by dependency, not by path prefix**. `POST /sessions/{id}/ask*`
  also lives under `/sessions` but must stay unguarded — it is the demo's second turn, and
  guarding it breaks follow-ups.

### Structural regression test

- The test that proves a future endpoint cannot be added unguarded must use a **recursive
  route walker with a non-vacuity assertion**. FastAPI 0.141.1 no longer flattens included
  routers: `include_router` leaves a `fastapi.routing._IncludedRouter` in `app.routes`, so
  the naive `for r in app.routes: if isinstance(r, APIRoute)` finds **zero** session routes
  and passes vacuously over a wide-open service. Follow the existing skip-detector
  convention at `tests/test_store_contract.py:441`.

### SSE error redaction

- Wire the existing, already-tested redaction helper into the SSE error handler
  (`service.py:263`). The `/health` path already uses it correctly — this is a missing call
  site, not new code.

### Claude's Discretion

- Exact name and module placement of the token-only dependency.
- Whether the sessions group becomes a separate `APIRouter` or takes per-route dependencies,
  provided the structural test can enforce the invariant either way.
- Header name for `SESSIONS_TOKEN` (following the existing `x-demo-token` convention is
  fine).
- Test fixture mechanics for the ~14 affected call sites.

</decisions>

<specifics>
## Specific Ideas

- Deploy sequence must fail closed at every intermediate state: `fly secrets set --stage`
  (verified to exist), then a single `fly deploy` that also carries Phase 10's three pending
  commits per ROADMAP's one-cutover note, then curl verification against the live host.
- SC-6 requires verification against the **deployed** service, not just locally: an
  unauthenticated `GET /sessions` from the open internet must return 401/403.
- `tests/test_service.py:807-815` breaks under every candidate design and needs an explicit
  fix, not a fixture-level sweep.

</specifics>
