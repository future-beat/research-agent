# Phase 22.5: The demo shows progress - Research

**Researched:** 2026-08-16
**Domain:** Server-Sent Events (SSE) streaming UX for an existing FastAPI + LangGraph service; no new
external dependencies
**Confidence:** HIGH

## Summary

The fix is exactly as small as CONTEXT.md frames it: `_stream` (`src/research_agent/service.py:379-445`)
already receives `{"node": "supervisor", "next_step": <target>}` as a normal LangGraph chunk on every
routing hop and currently discards it with `continue`. The supervisor's `routed_to` (the trace field;
the raw chunk key is `next_step` — see Q1 below) is the only signal that a node is *about to* run, and it
already exists on the wire path, computed by `graph.py:678`. Forwarding it costs one new `if` branch and
zero new state, zero new plumbing, and zero graph changes — matching the house constraint that this
phase touches no pipeline/model/routing logic.

The highest-leverage design decision is **reusing the `node` SSE event name with an additive `status`
field** rather than inventing a new event type. Verified against the real test suite (`tests/test_service.py`),
this choice keeps two Phase-19 gating tests (`test_stream_does_not_emit_supervisor_hops`,
`test_stream_carries_node_detail`) passing **with no code change at all**, and keeps the structural half of
a third (`test_stream_emits_progress_then_exactly_one_result`'s event-name and terminal-count assertions)
unchanged — only its payload-sequence assertion needs updating. A new event name (`stage`/`routing`)
would break all three mechanically, for no semantic gain: the client already dispatches on `event:` name,
so a `status` field inside the existing `node` branch is strictly less code on both sides of the wire.

On the client, the graph's own topology (`build_graph()` — every worker has exactly one edge back to
`supervisor`, and `supervisor`'s conditional edge selects exactly one target) makes execution strictly
sequential: only one node is ever in flight. That means row-keying does not need a map keyed by node
name (which would collide across the revision loop's repeated `writer`/`critic` occurrences) — a single
"the currently pending row" pointer is collision-proof by construction, because a start and its matching
completion always alternate for whichever node is in flight, never interleaved with another node's cycle.

CSP is self-healing by design (`csp.py` derives both hashes from the live file at request time,
cached only in-process) and none of the four CSP-shape tests hardcode a literal hash — but the edit
**must land inside the existing single `<script>...</script>` block**, or `test_demo_page_has_exactly_one_script_block_and_one_style_block`
goes red.

**Primary recommendation:** Forward every `routed_to` value except `"done"` as `_sse("node", {"node": routed_to, "status": "started"})`,
emitted from inside the existing `if node_name == "supervisor"` branch in `_stream` before its `continue`;
leave every completion payload (`_node_detail`'s output) byte-for-byte unchanged; upgrade a single
pending DOM row in place on the client rather than keying by node name.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Knowing what runs next | A client-side mirror of the routing table (inferring "next must be a writer revision" from a critic-rejected event) | The supervisor's own `routed_to`, already computed and already on the wire path | The routing table lives in exactly one place (`graph.py` supervisor, ADR-0001's whole premise); a second copy in JS drifts the first time a routing row changes and nothing would catch it |
| Detecting "the stream is genuinely dead" | A heartbeat/keepalive timer | Nothing — out of scope by CONTEXT.md; the repro proved the connection was never the problem | Building keepalive machinery to fix a UX problem that isn't a connectivity problem is solving the wrong layer |
| Distinguishing "started" from "terminal" client-side | A new SSE event name requiring a second dispatch branch | The existing `event: node` name plus a `status` field read inside the existing branch | One branch to maintain instead of two; `sawTerminal` logic (keyed on `name === "result"`/`"error"`) is untouched either way |

**Key insight:** every piece of state this phase needs (which node is next, what to label it, when it's done)
already exists somewhere in `graph.py` or `service.py`. The entire fix is *forwarding data across a
boundary that currently drops it* — never computing anything new.

## Q1 — The Supervisor's Data

**Read: `supervisor_node`, `src/research_agent/graph.py:600-711`.**

Every branch of `supervisor_node` sets exactly one field before returning:

```python
# graph.py:678
decision = {"node": "supervisor", "routed_to": state["next_step"]}
```

`decision` is appended to `state["trace"]` (visible only in the final trace / `/sessions/{id}/trace`,
never on the SSE wire today). The state field driving it is `state["next_step"]`, declared
`next_step: str` [VERIFIED: src/research_agent/graph.py:224] `next_step: str` and set by exactly nine
assignment sites, all inside `supervisor_node` [VERIFIED: src/research_agent/graph.py:622,625,632,649,661,666,668,670,672,674,676]:

```python
state["next_step"] = "done"        # x3: iteration cap, revision cap, budget cap
state["next_step"] = "researcher"  # x2: no-prior-notes followup, notes-insufficient followup
state["next_step"] = "classifier"  # topic_type not yet set
state["next_step"] = "researcher"  # no research_notes yet
state["next_step"] = author        # no draft yet — author is "writer" or "responder"
state["next_step"] = "critic"      # drafted but not reviewed
state["next_step"] = author        # reviewed but not approved (the revision loop)
state["next_step"] = "done"        # approved
```

`author = "responder" if state["mode"] == "followup" else "writer"` (`graph.py:613`). **All possible
`routed_to` values, exhaustively, from these nine sites:** `"classifier"`, `"researcher"`, `"writer"`,
`"responder"`, `"critic"`, `"done"`. This set is also asserted directly by `route()`'s own return type
annotation [VERIFIED: src/research_agent/graph.py:714-717] `Literal["classifier", "researcher", "writer", "responder", "critic", "__end__"]`
— `route()` maps `"done"` to LangGraph's `END` sentinel, confirming `"done"` is the one value with no
matching worker node.

**LangGraph chunk shape, confirmed against existing code.** `graph.app.stream(state)` is default
("updates") mode — `_stream`'s existing loop (`for node_name, node_state in chunk.items()`) already
relies on `node_state` being the **full** `AgentState` dict (not a partial delta), since `_node_detail`
reads `state["trace"][-1]`, `state["topic_type"]`, etc. for every non-supervisor node today. That means
when `node_name == "supervisor"`, `node_state["next_step"]` is directly readable — no new state
plumbing, no new trace lookup, just one more key read off the chunk that already arrives.

**Frequency, verified against the repro log:** the reproduction's `trace` array contains 9 supervisor
entries in a 183s run [source: `repro-2026-08-16.log:27`, the `trace` field of the terminal `result`
payload] — one per routing decision, matching `1 (classifier) + 1 (researcher) + 3×(writer+critic) + 1 (done)`
for a 2-revision run (`MAX_REVISIONS = 2` [VERIFIED: src/research_agent/graph.py:46]).

**Which of the 9 draw a stage the page doesn't already have — none are noise.** Every supervisor entry
except the final `routed_to: "done"` announces a genuinely new silence window the page cannot currently
show, including the revision-loop entries. The intuitive objection — "the page already draws `writer`
on completion, so routing back to it for a revision is redundant" — does not hold: the *completion*
event for a rejected critic tells the visitor nothing about what happens next, and the repro shows
5–12s gaps between each subsequent completion (`repro-2026-08-16.log:8-24`). Announcing "drafting the
report" the instant the supervisor routes there, rather than only once the writer finishes ~10s later,
is exactly the improvement Success Criterion 1 asks for on every hop, not only the first. `routed_to:
"done"` is the one value that must be filtered — it names no worker node, so a client rendering it would
either draw a garbage stage row or need a special case; simplest is to never emit it.

## Q2 — Event Shape, Decided

**Recommendation: reuse `event: node`, add an additive `"status": "started"` field. Do not introduce a
new event name.**

**The binding test.** `test_stream_emits_progress_then_exactly_one_result`
[VERIFIED: tests/test_service.py:1112-1127]:

```python
assert names[:-1] == ["node"] * (len(names) - 1)
assert names[-1] == "result"
assert names.count("result") == 1
assert [payload["node"] for _, payload in events[:-1]] == [
    "classifier", "researcher", "writer", "critic",
]
```

This test counts events **by name**. Reusing `"node"` for a starting event means the first three
assertions — the ones that literally encode "exactly one terminal event, everything else is `node`" —
**remain true without modification** once the extra started events are added, because every one of
them is still named `"node"`. Only the fourth assertion (the specific completion sequence) needs
updating, because now interleaved `started`/`completed` pairs appear for each node. A new event name
(e.g. `"stage"`) would break the first assertion mechanically — some entries would no longer be
`"node"` — for no test that currently exists to gain anything from the distinction.

**Does a starting event break "exactly one terminal event"?** No, by construction: only `result` and
`error` are terminal (client's `sawTerminal` flag is set only on those two names —
[VERIFIED: src/research_agent/static/index.html:385-391] `} else if (name === "result") { sawTerminal = true; ... } else if (name === "error") { sawTerminal = true; ...`).
A starting `node` event can never satisfy either branch. The mutation "a starting event counted as
terminal" is already covered by the unmodified `names.count("result") == 1` assertion — if a starting
event were ever mistakenly emitted as `event: result`, this line goes red without any new test.

**`test_stream_does_not_emit_supervisor_hops` needs zero changes.** [VERIFIED: tests/test_service.py:1130-1138]:

```python
assert all(payload["node"] != "supervisor" for name, payload in events if name == "node")
assert any(e["node"] == "supervisor" for e in events[-1][1]["trace"])
```

Because the recommended payload sets `"node"` to the **routed-to target** (e.g. `"researcher"`), never
literally `"supervisor"`, the first assertion stays true — this test is direct evidence the fix is
additive to an existing contract, not a violation of it. The second assertion is about the final
`trace` field, which `graph.py` produces unchanged. **This test is a strong "must not change" signal:**
if a plan needs to edit it, that's a sign the design deviated from what CONTEXT.md and this research
recommend.

**`test_stream_carries_node_detail` also needs zero changes** under the current fixture (no revision
loop; `critic_verdicts=("APPROVED",) * 8` is `make_client`'s default —
[VERIFIED: tests/test_service.py:185]). It builds `detail = {payload["node"]: payload for _, payload in
sse_events(response) if _ == "node"}` — a dict keyed by node name, last write wins. Because a started
event for a node always precedes that node's own completion in the stream, and no node repeats in the
default fixture, the dict's final entry per key is always the completion payload, so
`detail["classifier"]["topic_type"]` and `detail["critic"]["approved"]` are unaffected.

**What `_node_detail` does, and why a starting event should NOT call it.**
[VERIFIED: src/research_agent/service.py:447-462]:

```python
def _node_detail(node_name: str, state: dict) -> dict:
    detail: dict[str, Any] = {}
    if node_name == "classifier":
        detail["topic_type"] = state["topic_type"]
    elif node_name == "researcher":
        detail["recalled_from_memory"] = state["trace"][-1].get("recalled_from_memory", 0)
    elif node_name in ("writer", "responder"):
        detail["revision"] = state["revision_count"]
    elif node_name == "critic":
        detail["approved"] = bool(state["approved"])
    ...
```

Every field it reads is **post-execution** data: `topic_type` doesn't exist until the classifier has
run, `state["trace"][-1]` is the node's *own* trace entry (appended just before return), and
`state["approved"]` is the critic's own verdict. At routing time — before the node has run — none of
this exists yet. Worse, `revision_count` for the writer is misleading if read pre-node: it is
**incremented inside `writer_node` itself**, only `if is_revision` (`graph.py:464-465`), so at the
moment the supervisor routes back to `writer` for the second time, `state["revision_count"]` still
holds its **pre-increment** value — identical to the value before the *first* writer call. Attempting to
label a starting event with "revision N" would either require duplicating writer-internal logic or
would silently misreport. **A starting event needs no payload beyond the node name and a status
marker** — `{"node": routed_to, "status": "started"}` — the label alone (via the client's existing
`LABELS` map) carries all the meaning a visitor needs at that instant; the accurate revision/approval
detail arrives moments later on the real completion event, unchanged.

**Recommended code, `_stream`** (the one line CONTEXT.md points at, replaced with four):

```python
# service.py:391-396, current:
for chunk in graph.app.stream(state):
    for node_name, node_state in chunk.items():
        final_state = node_state
        if node_name == "supervisor":
            continue  # fires between every node; pure noise on the wire
        yield _sse("node", {"node": node_name, **_node_detail(node_name, node_state)})

# proposed:
for chunk in graph.app.stream(state):
    for node_name, node_state in chunk.items():
        final_state = node_state
        if node_name == "supervisor":
            routed_to = node_state["next_step"]
            if routed_to != "done":
                yield _sse("node", {"node": routed_to, "status": "started"})
            continue
        yield _sse("node", {"node": node_name, **_node_detail(node_name, node_state)})
```

No change to `_node_detail`, `_sse`, `_sse_response`, `run_finished`/`run_failed` logging, or the
`result`/`error` yield sites. `[ASSUMED: exact final code shape — the planner should confirm the
line numbers still match at execution time, since Phase 21.5 and 22 may have shifted them slightly]`.

## Q3 — Client Rendering, Decided

**Recommendation: a single pending row upgraded in place — NOT a map keyed by node name, and NOT a
separate "current stage" line.**

**Why keying by node name is a trap (the objective's own warning, confirmed against the code).** The
revision loop draws `writer` and `critic` multiple times — 3 times each in the repro
(`repro-2026-08-16.log:8-24`: `writer` at +132s/+155s/+178s, `critic` at +143s/+167s/+183s). A row
store like `{ writer: <row>, critic: <row> }`, upgraded by looking up `data.node`, would have the
*third* writer's completion overwrite/upgrade the row created for the *first* writer's start — either
silently reusing a stale DOM node or leaving two of the three writer rows permanently pending. This is
exactly the collision the objective flags.

**Why it's avoidable entirely, not just fixable: the graph never runs two nodes concurrently.**
[VERIFIED: src/research_agent/graph.py:720-744] `build_graph()`'s topology has every worker node
(`classifier`, `researcher`, `writer`, `responder`, `critic`) wired with a single edge back to
`"supervisor"` (`for worker in (...): graph.add_edge(worker, "supervisor")`), and `supervisor`'s own
`add_conditional_edges` selects exactly one of six targets per hop. There is no fan-out, no parallel
branch, anywhere in this graph. Combined with `graph.app.stream()`'s synchronous, single-threaded
execution, **only one node is ever "in flight" at any moment.** That means a start event and its
matching completion always alternate strictly — nothing else can arrive between them. Row identity by
node NAME is therefore unnecessary; row identity by SEQUENCE POSITION ("the one pending row right now")
is sufficient and cannot collide, at zero added state beyond two variables.

**Existing row lifecycle, read.** [VERIFIED: src/research_agent/static/index.html:229-237,381-384]:

```javascript
function stage(node, detail) {
  const row = el("div", "stage");
  row.appendChild(el("span", "dot"));
  const label = el("span");
  label.appendChild(el("b", null, LABELS[node] || node));
  if (detail) label.appendChild(document.createTextNode(" — " + detail));
  row.appendChild(label);
  return row;
}
...
if (name === "node") {
  const row = stage(data.node, nodeDetail(data.node, data));
  row.classList.add(data.node === "critic" && !data.approved ? "rejected" : "done");
  stages.appendChild(row);
}
```

Today every `node` event unconditionally **creates and appends a new, already-`done`-or-`rejected`
row**. There is currently no "pending" visual state at all — this is precisely the bug: the page has no
representation of "in progress," only "finished."

**CSS already has an unstyled default that is exactly a pending state — no new CSS required.**
[VERIFIED: src/research_agent/static/index.html:82-84]:

```css
.stage .dot { width: .5rem; height: .5rem; border-radius: 50%; background: var(--muted); flex: none; }
.stage.done .dot { background: var(--ok); }
.stage.rejected .dot { background: var(--warn); }
```

A row with **neither** `.done` nor `.rejected` already renders with the muted dot color. Appending a
row without either class at start time, then adding the right class on completion, requires **zero
edits to the `<style>` block** — which matters for CSP scope: any edit to the `<style>` block changes
its hash regardless of size, so leaving it untouched is strictly the smaller diff (still self-heals via
`csp.py` either way, but smaller diff = smaller review surface for a hotfix).

**Recommended client logic** (inside the existing `if (name === "node")` branch, replacing the four
lines above):

```javascript
let pendingRow = null;   // the one row currently in flight, or null
let pendingNode = null;  // its node name, for the (should-never-happen) mismatch fallback

...
if (name === "node") {
  if (data.status === "started") {
    pendingRow = stage(data.node, null);
    pendingNode = data.node;
    stages.appendChild(pendingRow);
  } else if (pendingRow && pendingNode === data.node) {
    // Upgrade in place: same row object, now with real detail and its final class.
    const label = pendingRow.lastChild;
    label.textContent = "";
    label.appendChild(el("b", null, LABELS[data.node] || data.node));
    const detail = nodeDetail(data.node, data);
    if (detail) label.appendChild(document.createTextNode(" — " + detail));
    pendingRow.classList.add(data.node === "critic" && !data.approved ? "rejected" : "done");
    pendingRow = null;
    pendingNode = null;
  } else {
    // Defensive fallback only — should be unreachable given the graph's
    // strict sequencing (Q3). A completion with no matching pending row
    // still renders correctly, just without the "upgrade" animation.
    const row = stage(data.node, nodeDetail(data.node, data));
    row.classList.add(data.node === "critic" && !data.approved ? "rejected" : "done");
    stages.appendChild(row);
  }
}
```

**The finished transcript stays readable** because the upgrade is in-place DOM mutation, not
append-then-hide: the final rendered row count after a run equals exactly the number of *completed*
node events, identical to today's output — the only visible difference during a live run is that a
"drafting the report" row (muted dot) appears before its "drafting the report — revision 2" (green
dot) counterpart replaces it, never both existing side by side.

## Q5 — Test Surface

**How the existing streaming tests drive `_stream`.** [VERIFIED: tests/test_service.py:1-40,161-227,
185]. The app under test is the **real** FastAPI app with the **real** `graph.app` (real
`supervisor_node`, real routing, real `StateGraph`) — only the Anthropic client is faked, via
`monkeypatch.setattr(graph, "client", lambda: fake)` where `fake = FakeClient(critic_verdicts)`. The
default `critic_verdicts=("APPROVED",) * 8` (`make_client`'s `build()` default) means most existing
tests exercise the **no-revision** path. This is significant: it means server-side tests can
deterministically script a multi-revision run (as the repro happened to hit in production) by passing
`critic_verdicts=("REJECTED", "REJECTED", "APPROVED", ...)` to `build()` — the exact mechanism already
used elsewhere in this suite for critic-loop tests — without touching the graph itself.

**Asserting "a starting event fires BEFORE its completion event," precisely.** Filter the parsed SSE
events to `name == "node"` and payloads for one target node name, then assert `status` values appear
in order `["started", None]` (or whatever key the plan settles on for "this is a completion") with the
started entry's list index strictly less than the completion's:

## Common Pitfalls

### Pitfall 1: Emitting a starting event for `routed_to: "done"`
**What goes wrong:** A row is drawn for a node called "done" with no `LABELS["done"]` entry, falling
back to the raw string `"done"` (`LABELS[node] || node` in `stage()`), and it is never resolved because
no `"done"` completion event exists — an orphaned row exactly like the ones Success Criterion 2
forbids.
**Why it happens:** The naive "forward every supervisor hop" reading of CONTEXT.md's fix description
doesn't distinguish the one value with no matching worker.
**How to avoid:** Filter `if routed_to != "done":` before yielding, exactly as shown in Q2's code.
**Warning signs:** A visible "done" stage row on every run, always the last one, never turning green.

### Pitfall 2: Reintroducing a node-name-keyed row map on the client
**What goes wrong:** The second and third writer/critic rows in a revision loop either overwrite the
first row's DOM node (visually "jumping" between revision labels) or never get upgraded at all,
leaving 2 of 3 writer rows permanently pending after the run has finished.
**Why it happens:** "Key the pending row by node name" is the obvious first design, and it works
correctly for a single-pass run — the bug only appears once a critic rejection triggers a second pass,
which most manual smoke-testing (a single "why?" question that gets approved first try, as in the
default test fixture) will never exercise.
**How to avoid:** Use the single-pointer design from Q3 (`pendingRow`/`pendingNode`, cleared on every
completion), which is collision-proof by construction given the graph's strict sequencing — no name
lookup at all.
**Warning signs:** Only surfaces under `critic_verdicts` scripted with at least one `"REJECTED"` —
default test fixtures and default manual demo questions won't catch it.

### Pitfall 3: Editing `index.html`'s `<script>` block into two blocks
**What goes wrong:** `csp.py`'s `policy()` raises `ValueError` naming the counts
(`src/research_agent/csp.py:128-133`), and `GET /` with `Accept: text/html` starts returning a 500
instead of the demo page — this is the "fails loudly instead of serving a broken policy" behavior
`policy()`'s own docstring describes, so it will be caught immediately by
`test_demo_page_is_served_with_a_hash_based_csp`, but it's worth knowing in advance rather than
discovering via a red CI run.
**Why it happens:** Adding a `<script defer>` tag, or splitting logic into a second inline `<script>`
for readability, both look harmless in isolation.
**How to avoid:** All new JS lives inside the file's single existing `<script>...</script>` pair.
**Warning signs:** `test_demo_page_has_exactly_one_script_block_and_one_style_block` red locally before
any push.

### Pitfall 4: Assuming the researcher's own runtime bounds the visible gap
**What goes wrong:** Success Criterion 4 ("the gap a visitor sees ... is bounded by the supervisor's
routing, not by the researcher's runtime") is easy to misread as requiring the researcher to run
faster — explicitly out of scope (CONTEXT.md's Deferred Ideas). The actual claim is about *when the
signal fires*, not *how long the work takes*.
**Why it happens:** The repro's headline number (120s) is about the researcher's runtime, inviting a
performance-fix framing.
**How to avoid:** The fix bounds the gap between the *researcher's own started event* and the
*classifier's completion* — that gap is milliseconds (the supervisor hop is plain Python, no model
call), not the 120s of web search. What changes is that the visitor now sees "searching the web"
appear almost immediately after "classifying the topic" completes, instead of staring at a stale label
for the full 120s.
**Warning signs:** A plan task that touches `researcher_node`'s search strategy, timeout, or model
config is out of scope for this phase.
