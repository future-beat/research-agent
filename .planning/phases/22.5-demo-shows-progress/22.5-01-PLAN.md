**P-01 — Event shape: reuse `event: node`, add an additive `"status": "started"` field. No new
event name.** 22.5-RESEARCH Q2's binding argument: `test_stream_emits_progress_then_exactly_one_result`

a `stage`/`routing` event name breaks them mechanically for no test that exists to gain

this as cosmetic; it is locked here only so both sides of the wire agree).

**P-02 — The started payload is exactly two keys: `node` (the routed-to target) and `status`.
`_node_detail` is never called for it.** Every field that helper returns is post-execution
(service.py:447-462): `topic_type` does not exist until the classifier has run, `trace[-1]` is
the node's own entry, and `revision_count` is incremented INSIDE `writer_node` only when the
pass is a revision (graph.py:464-465) — so at the moment the supervisor routes back to the
writer, the value still reads pre-increment and a "revision N" label would silently misreport.
The label alone carries all the meaning a visitor needs at that instant; the accurate detail
arrives moments later on the unchanged completion event.

**P-03 — `routed_to == "done"` emits nothing.** It is the one value of the six that names no
worker node (`route()`'s Literal, graph.py:714-717, maps it to `END`). `LABELS` has no `done`
entry, so `LABELS[node] || node` would draw a literal "done" row that no completion event can
ever resolve — an orphaned row, exactly what Success Criterion 2 forbids (Pitfall 1).

**P-04 — The client keeps ONE pending-row pointer, declared inside `run()` beside
`sawTerminal` — not a node-name-keyed map, and not module scope.** Not a map because the
revision loop draws writer and critic three times each (repro-2026-08-16.log:8-24) and a
name-keyed store would have the third writer's completion upgrade the first writer's row,
leaving two rows permanently pending — a bug that only appears once a critic rejects, which
no default fixture and no lucky manual smoke test will ever reach (Pitfall 2). One pointer is
collision-proof by construction rather than by care: the graph has no fan-out anywhere (every
worker has a single edge back to supervisor, graph.py:730-731; the conditional edge selects
exactly one target, graph.py:733-744), so only one node is ever in flight. Per-run scope rather
than the research listing's module-level `let`: `stages` is already per-run, the pointer's
lifetime must match the DOM it points into, and a failed or abandoned run must not leak a
pointer into the next one.

**P-05 — Completion upgrades the row by APPENDING the detail text node, never by rebuilding
the label.** 22.5-RESEARCH Q3's listing clears and rebuilds the label span; that is dead work
here. The `<b>` was built from `LABELS[data.node]` on the started event and the pointer's
node-name guard proves it is the right one, so the only thing a completion adds is the
`" — " + detail` text node and the final class. Smaller diff, fewer page bytes, same render.

**P-06 — Zero CSS edits, and all new JS inside the existing single `<script>` block.**
`.stage .dot`'s `background: var(--muted)` default (index.html:82-84) is ALREADY a pending
state — a row with neither `.done` nor `.rejected` renders muted today — so the `<style>` block
is not touched at all and its bytes are asserted identical. A second `<script>` block, or an
attribute on the existing one, makes `csp.policy()` raise (csp.py:128-133) and `GET /` return
500; `inline_blocks`'s regex only matches bare tags, which is why the shape gate exists.

**P-07 — The completion branch's "no pending row" arm is a supported path, not defensive
decoration.** It is today's behaviour verbatim, and it is what keeps the page correct against a
server that never sends started events — a stale cached page, or a rollback. Do not delete it
as unreachable. Symmetrically: a run that ends in `error` leaves its in-flight row pending with
a muted dot, which is the honest rendering (that stage genuinely never finished); no cleanup
is added for it.

**P-08 — `test_stream_does_not_emit_supervisor_hops` and `test_stream_carries_node_detail` are
NOT edited, docstrings included.** Their being untouched is a phase deliverable
(22.5-VALIDATION's sign-off), because it is the evidence that this change is additive to an

name, so the first test's assertion stays true, and the second's dict-keyed-by-name

precedes its own completion). The first test's docstring also remains literally accurate — the
supervisor's own name never reaches the wire. If the executor believes otherwise, argue it in
the SUMMARY; do not edit the file.
