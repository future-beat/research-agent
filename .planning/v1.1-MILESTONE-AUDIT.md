file at commit `3acaec7`. Six were deliberate reversals, each superseding a numbered ADR
rather than quietly contradicting prose:

| Reversal | Record |

## Integration: 8/8 wired, 4/4 flows complete

The integration checker drove all four E2E flows through the real app and found **no
blockers and no orphaned exports**. Two findings deserve attention.

### W1 — the blocking route can lose a run from the ledger (real defect)

Confirmed by reading source, not inferred. In `_execute` the `try` wraps *only*
`graph.app.invoke`; `on_complete` and `metrics.record` sit outside it. In `_stream` both
sit inside. The checker's probe:

```
BLOCKING _execute: reservation left={'2cf478ad…'} runs_recorded=0 cap_sees=$0.0000
STREAM   _stream:  reservation left=set()          runs_recorded=1 cap_sees=$0.3100
```

Triggers are realistic: a concurrent operator `DELETE` during a run, or a Postgres write
failure — which Phase 11 makes plausible by giving writes only the checkout-level retry.
The reservation half self-heals after 900s. **The ledger half never does**: that run's real
cost never reaches `runs`, so the daily cap is permanently blind to it. Phase 17 raised the
lost amount from a follow-up's pennies to a research-class $0.25–0.32.

This is the one finding I would fix before calling the milestone sealed.

### W2 — the reservation's arithmetic is stale, and a test defends it

`limits.py:136` states a typical run is `~$0.18 (under $0.20)`. The milestone's own closing
live check measured **~$0.25–0.32**. The documented trigger for revisiting the knob — the
2026-09-01 Sonnet boundary — has effectively already fired via the Opus critic instead.
`tests/test_limits.py:724` asserts `"0.18" in doc`, so the tree actively resists correction.

The cap still *bounds* spend, because `settle()` replaces the estimate with real cost. What
no longer holds is the honesty claim the phase made for the number.

## P1 — no phase has a VERIFICATION.md

The audit workflow treats a missing `VERIFICATION.md` as a per-phase blocker. **All nine
phases are missing one**, because every phase ran plan → execute → PR without the verify
step.

I am recording this as **process debt, not as eleven unsatisfied requirements**, and the
reasoning should be visible rather than assumed:

- Each phase shipped with a VALIDATION contract, gate batteries, mutation probes, and — for
  seven of nine — live production evidence.
- The integration checker independently re-derived the wiring and found 8/8 connections and
  4/4 flows.
- Calling the requirements unsatisfied would say something false about the system.

But the artifact the framework expects does not exist, and a future reader running this
audit will hit the same wall. That is a real gap in how this milestone was run.

## What the milestone got right, worth keeping

- **Vacuous gates became the project's signature find.** Sixteen-plus across seven phases,
  and the discipline compounded: waves routinely ran 10–15 mutation probes against plans
  naming 3, and twice a probe *passed and the probe itself was wrong* and was re-targeted
  rather than banked.
- **Plans were wrong about their own arithmetic and file paths at least five times**, and
  executors trusted the tree over the plan every time, recording the deviation.
- **The strongest reversal produced its own best argument at execution time**: Phase 17
  discovered that under the old design the refusal text *was* the shipped answer,
  critic-approved because it claimed nothing.

## Recommended before completing the milestone

1. **Fix W1** — move `on_complete` and `metrics.record` inside `_execute`'s try, matching
   `_stream`. Small, and it closes a permanent hole in the cap's input.
2. **Correct W2** — update the four documents and the test that pins `0.18` to the measured
   figure, or state plainly that the reservation is a floor rather than a typical.
3. **Reconcile the five VALIDATION contracts** — flip the frontmatter and mark the rows for
   10.5, 12, 14, 16, 17 against the evidence already in their SUMMARYs.
4. Optionally address P1 for the record.

Items 1 and 2 are a small closure phase. Item 3 is bookkeeping.
